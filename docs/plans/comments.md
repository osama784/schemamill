# Comments — model, import, diff, plan, render, round-trip

**Status:** built · **Last updated:** 2026-11-24

Every comment on a modeled entity survives dump import → model → diff → plan → render → apply → dump import: tables, columns, sequences, plain and materialized views, primary keys, unique/check/foreign-key constraints, standalone indexes, and — since [#91](https://github.com/osama784/schemamill/issues/91) — extensions; a constraint-backed index's own comment has no model slot, so both the import's `USING INDEX` splice and the live catalog's backing-index read flag it as `dropped comment from <schema>.<index>`, matching the plain `pg_dump` flow ([#213](https://github.com/osama784/schemamill/issues/213), [ADR 0030](../adr/0030-constraint-backed-index-comments-are-flagged.md)). The slice shipped in [#87](https://github.com/osama784/schemamill/issues/87) as Slice C of the [import long-tail plan](./import-long-tail.md), after views, so comments were modeled once, on the families that existed when they landed; the extension target followed in the [extensions slice](./extensions.md). Its durable decisions are recorded in [ADR 0021](../adr/0021-comments-travel-the-model.md).

## Goal

A dump's comments — the seven `COMMENT ON` object forms this slice modeled, plus the extension form added in [#91](https://github.com/osama784/schemamill/issues/91) — import onto their entities, compare as their own change, plan in a terminal phase, render with PostgreSQL-correct literal quoting, and re-import unchanged; a recreated constraint, index, or materialized view re-asserts its comment instead of losing it to the drop.

## Scope

**In:** `comment?: string` on the nine entity interfaces this slice carried (the extension entity gained one in [#91](https://github.com/osama784/schemamill/issues/91)); import of `COMMENT ON TABLE`, `COLUMN`, `SEQUENCE`, `VIEW`, `MATERIALIZED VIEW`, `INDEX`, and `CONSTRAINT` (plus `EXTENSION` since [#91](https://github.com/osama784/schemamill/issues/91)); `comment-changed`; the `CommentTarget` union and one transactional `comment` step; the terminal global phase 12; canonical rendering with plain and `E'…'` literals and NUL refusal; CLI display and the `comments` golden scene; the workspace `comment` key; and the `comment-round-trip` live scene with server-derived cross-import checks.

**Out, named — never silent:** comments on extensions, listed here when this slice landed, have since shipped in the [extensions slice](./extensions.md) ([#91](https://github.com/osama784/schemamill/issues/91)); comments on unmodeled families (schemas, functions, procedures, triggers, rules, policies, types, foreign tables, tablespaces, roles, databases) — skipped and named as before; comments on PostgreSQL 18 named not-null constraints, listed here when this slice landed, have since shipped in [#147](https://github.com/osama784/schemamill/issues/147) ([ADR 0038](../adr/0038-not-null-constraint-comments-travel-the-model.md)); catalog introspection of comments — shipped for tables, columns, sequences, views, and materialized views in [#146](https://github.com/osama784/schemamill/issues/146) ([ADR 0026](../adr/0026-catalog-comment-reads.md)), and for primary-key, unique, check, foreign-key, and standalone-index comments in [#192](https://github.com/osama784/schemamill/issues/192) ([ADR 0028](../adr/0028-catalog-constraint-and-index-comments.md)); grants, ownership, and security labels ([#92](https://github.com/osama784/schemamill/issues/92)); view output columns, including their comments ([#143](https://github.com/osama784/schemamill/issues/143)); and `COMMENT ON` deparse ([#57](https://github.com/osama784/schemamill/issues/57)).

**Deliberately shallow for now:** a comment is text the model stores and compares verbatim; it is never parsed, normalized, or used as identity, and the engine does not attempt to merge conflicting comments on the same server object.

## Decisions

- **Model field, absent or non-empty.** Each entity carries `comment?: string`, stored verbatim — exact characters, unicode and newlines allowed. Absent means no comment. The empty string is not a model value: PostgreSQL reduces `COMMENT … IS ''` to the same removal case as `IS NULL`, and `pg_dump` never emits `IS NULL`, so the equivalence is semantic, not a fidelity loss. The workspace parser rejects `""` and text carrying NUL; the renderer refuses NUL again.
- **Descriptive, not structural.** `comment` is excluded from every structural equality function and from every field-change union, and never enters `ColumnAttributes`. A comment-only change must not decompose a constraint or index into a destructive drop and add.
- **One target union, one step.** `CommentTarget` has one variant per `COMMENT ON` object form; `view` carries `materialized`, and the index and constraint variants carry the node so the renderer can synthesize an unnamed node's conventional server name. One `comment` step carries `text`, absent meaning `IS NULL`, and every copied target strips the node's own `comment` so `text` is the only rendered value.
- **One change, appended last.** `diff` returns the table, sequence, view, and extension groups, then `diffComments` in target identity order. A comment the baseline lacks is an addition; a removed entity emits nothing; an entity whose structural identity changed reads as absent and reports an addition. The plan posts one `comment` step per change.
- **Terminal phase 12.** Every comment step — the diff's changes and the recreate re-assertions alike — lands in `application.comments`, and the plan appends the bucket after every structural and identity phase and before the extension teardown (phase 13). Every target exists by then: tables, columns, constraints, and indexes from the table phases, views from phase 7, sequences from phases 3 and 9, identities from phase 11, extensions from phase 1. Comments never affect structure and are order-insensitive among themselves.
- **Recreate re-assertion.** A drop takes the comment with the object, so seven recreate sites push a comment step when the target node states one: index, primary key, foreign key, unique constraint, check constraint, materialized or kind-change view, and the synthesized dependent foreign key whose referenced primary key changes. Both a recreate step and a diff change may name one target; the terminal phase keeps one step per target, and both carry the target's text. A removal is never suppressed.
- **Known ambiguity, recorded.** Two structurally identical unnamed nodes with different comments share one `CommentTarget` key, so the terminal phase keeps one step. The model already cannot distinguish the two server objects on apply, and the workspace does not forbid the shape; the behavior is documented rather than hidden.
- **Literal quoting.** A line-safe comment renders as `'…'` with embedded quotes doubled; a backslash or any C0/DEL control switches to `E'…'`, escaping `\`, `'`, newline, carriage return, tab, and other controls as `\xHH`. The one-statement-per-line contract survives a multi-line comment, unicode passes through unchanged, and NUL throws `RenderRefusalError`.
- **Resolution before canonicalization.** The importer resolves a comment against the stored server name while drafts still carry it — `finalizeTable` canonicalizes after every statement — and falls back to the conventional synthesized name for a node the source declared unnamed. A collision-suffixed name is not stripped, so the comment resolves directly. No comment-aware canonicalization branch exists.
- **Flags, not silence.** An unresolvable target, a kind mismatch, a view output column, and NUL-carrying text are flagged as `dropped comment from <object>`; unmodeled families keep the existing `skipped COMMENT ON <KIND> <object>` path; a PostgreSQL 18 named not-null constraint instead retains its text as the column's `notNullComment` with no flag, while a generated name still strips and the renderer re-synthesizes it ([#147](https://github.com/osama784/schemamill/issues/147), [ADR 0038](../adr/0038-not-null-constraint-comments-travel-the-model.md)).
- **A consumed index's comment is flagged, never copied.** An `ADD CONSTRAINT … USING INDEX` that consumes a plain unique index reads the index's `comment` before the splice and drops it: the model has no slot for a constraint-backed index's description, so the comment is flagged `dropped comment from <schema>.<index>` on the ALTER statement. The flag names the object the statement leaves behind: the built constraint's name when the statement applies (PostgreSQL renames the consumed index to it), the source index's name when the declaration is deduped onto an equal retained node or rejected as an additional primary key (the server rejects the statement, so no rename happens). The retained constraint keeps its own comment — a dedupe or rejection never compares the two, and identical text is flagged too, because nothing is copied. A `COMMENT ON INDEX` arriving after consumption resolves in no table draft — the index is gone — so it takes the same `dropped comment from <index>` flag; a later `COMMENT ON CONSTRAINT` attaches normally. A pre-fix workspace whose copied comment lived on the constraint re-imports as a comment removal — the plan's `COMMENT ON CONSTRAINT … IS NULL` is a no-op against the database whose `pg_constraint` description is empty — and reverting the slice restores the copied shape ([#213](https://github.com/osama784/schemamill/issues/213), [ADR 0030](../adr/0030-constraint-backed-index-comments-are-flagged.md)). The same flag now covers a comment on an exclusion constraint's backing index in both the dump import and the live catalog; and [ADR 0035](../adr/0035-exclusion-backing-index-comments-are-flagged.md) records the backing-index policy ([#231](https://github.com/osama784/schemamill/issues/231)). The exclusion constraint's own comment is no longer deferred: it travels on `ExclusionConstraint.comment` through a new `exclusion-constraint` `CommentTarget` and the terminal comment phase, cataloged from `obj_description(oid, 'pg_constraint')`, as recorded in [ADR 0041](../adr/0041-exclusion-constraints-and-index-expressiveness-travel-the-model.md) ([#90](https://github.com/osama784/schemamill/issues/90)).
- **Last definition wins.** `IS NULL` and `IS ''` clear the field, a repeated comment replaces the earlier one, and a repeated `CREATE TABLE`/`SEQUENCE`/`VIEW` replaces the entity wholesale and therefore clears its comment, consistent with the import's existing last-definition rule.
- **Workspace compatibility.** `comment` joins each entity's key list and each serializer and parser; a pre-slice model file without the key reads unchanged, while an older binary fails closed on the new key (ADR 0010). No format version is introduced.

## Import envelope

`translateStatement` routes the eight modeled `CommentStmt` object kinds to `translateCommentStatement` before the generic skip fallback. The object lists and arity defaults:

| `objtype` | Object list | Target | Arity default |
| --- | --- | --- | --- |
| `OBJECT_TABLE` | `[schema, table]` | table | 1 → `public` |
| `OBJECT_COLUMN` | `[schema, table, column]` | column | 2 → `public`; 1 unresolvable |
| `OBJECT_SEQUENCE` | `[schema, name]` | sequence | 1 → `public` |
| `OBJECT_VIEW` | `[schema, name]` | plain view | 1 → `public` |
| `OBJECT_MATVIEW` | `[schema, name]` | materialized view | 1 → `public` |
| `OBJECT_INDEX` | `[schema, index]` | the one table's index of that stored or synthesized name | 1 → `public` |
| `OBJECT_TABCONSTRAINT` | `[schema, table, constraint]` | primary key, unique, check, or foreign key | 2 → `public` |
| `OBJECT_EXTENSION` | `<name>` (a `String` node, never a name list) | extension | bare name; never schema-qualified, resolved only against an imported extension ([#91](https://github.com/osama784/schemamill/issues/91)) |

Constraint resolution searches the table draft's primary key, unique constraints, check constraints, and foreign keys by stored or synthesized name, then the columns' named not-null facts (now retaining the text as `notNullComment`; [#147](https://github.com/osama784/schemamill/issues/147), [ADR 0038](../adr/0038-not-null-constraint-comments-travel-the-model.md)), then the generic flag — the fixed order recorded in ADR 0021. A view or materialized-view output-column comment resolves in no table draft, so it takes the generic `dropped comment` flag; view output columns are [still unmodeled](./views.md) ([#143](https://github.com/osama784/schemamill/issues/143)).

## Display

A comment target prints as the `COMMENT ON` object form, then the identity the model carries:

- named, non-unique: `index public.users (email) — users_email_idx`
- named, unique: `unique index public.users (email) — users_email_idx`
- unnamed, non-unique: `index public.users (email)` — unchanged
- unnamed, unique: `unique index public.users (email)` — only the `unique ` modifier is new

The modifier and the em-dash name suffix follow `formatIndex`'s established grammar, so a comment line and a structural index line name an index the same way. A named index's stored name is its identity — `indexIdentity` pairs and compares by name — so it is printed; a constraint's stored name is not identity (a constraint pairs by structure), so it stays off the line. An unnamed index is keyed by its structure — `unique` plus ordered columns — and its server name is synthesized only at render time.

The unnamed unique shape deviates from [#148](https://github.com/osama784/schemamill/issues/148)'s literal "unnamed indexes keep their current rendering": with no name to print, the `unique ` modifier is the only thing that makes a uniqueness difference produce a distinct line, so it gains that modifier and nothing else. This is a recorded deviation, not an accident.

Identifiers print raw, as everywhere else in CLI display: an index name containing spaces, quotes, or newlines is neither quoted nor escaped (the deferred raw-identifier residual). The `comments` golden scene pins the named-unique and unnamed non-unique shapes in compare and plan, including the unnamed status line's unchanged spelling.

## Evidence

The package suites pin the contract level by level; the CLI `comments` scene pins compare and plan bytes, including the terminal phase and the JSON-quoted display; and the postgres `comments.sql` golden pins all seven statement forms, `IS NULL`, and the escape matrix. The corpus is 564 postgres tests + 63 scenes + 4 always-on live subtests = 631 tests across 63 scenes, and the five PostgreSQL 18 scenes, `not-null-constraint-names` among them, are floored with 5 skipped. No local `SCHEMAMILL_TEST_PG_URL` was configured, so live pass/skip counts come from CI only; the `verify-postgres` job runs the same harness on PostgreSQL 18. The `comment-introspection` scene carries the `matches-import` assertion: its catalog read returns the comment-carrying table, columns, standalone sequence, views, and materialized view, and deep-equals the applied dump's import. Both comment scenes still assert `matches-import`: `comment-round-trip` also carries constraint and index comments, and its catalog read returns the whole comment-carrying model ([#192](https://github.com/osama784/schemamill/issues/192), [ADR 0028](../adr/0028-catalog-constraint-and-index-comments.md)). The `constraint-backed-index-comments` scene asserts `flags` instead, because both read paths now report the constraint-backed index comments rather than carrying them ([#213](https://github.com/osama784/schemamill/issues/213), [ADR 0030](../adr/0030-constraint-backed-index-comments-are-flagged.md)).

## Acceptance

- Comments on the ten modeled entities import, diff, plan, and render without silent loss: a consumed index's comment is flagged, never copied — the model has no slot for a constraint-backed index's description — against the built name when the attachment applies and the source name when it is deduped or rejected, and a comment on an unnamed constraint or index survives canonicalization.
- A recreated index, primary key, foreign key, unique or check constraint, materialized view, or dependent foreign key re-asserts its comment exactly once in the terminal phase.
- Workspace read compatibility, the goldens, and the gated scene pass; all five gates are green and `pnpm docs:counts --check` reports no stale claim.

## Deferred

Named, never silent:

- **Comments on extensions** — closed in [#91](https://github.com/osama784/schemamill/issues/91): `COMMENT ON EXTENSION` now imports, plans in the terminal comment phase, and renders ([extensions plan](./extensions.md)).
- **Comments on unmodeled families** — schemas, functions, procedures, triggers, rules, policies, types, foreign tables, tablespaces, roles, and databases stay skipped and named.
- **Comments on PostgreSQL 18 named not-null constraints** — closed in [#147](https://github.com/osama784/schemamill/issues/147): `COMMENT ON CONSTRAINT` on a named not-null imports onto the column as `notNullComment` with no flag (a generated name still strips), travels as a `not-null` `CommentTarget` in the terminal comment phase, renders back with `notNullName ?? synthesizedNotNullName`, and reads back from the live catalog on PostgreSQL 18 ([ADR 0038](../adr/0038-not-null-constraint-comments-travel-the-model.md)); the fact stays a column attribute — no not-null entity was added.
- **Comments on a consumed constraint that is deduped or rejected** — closed in [#171](https://github.com/osama784/schemamill/issues/171): the retained constraint keeps its own comment, and a consumed index comment is flagged `dropped comment from <schema>.<index>` on the ALTER statement — against the built name when the statement applies and the source index's name when it is deduped or rejected; the earlier "identical text stays silent" rule is retired for consumed comments, because nothing is copied ([#213](https://github.com/osama784/schemamill/issues/213), [ADR 0030](../adr/0030-constraint-backed-index-comments-are-flagged.md)).
- **Catalog introspection of comments** — shipped for tables, columns, sequences, views, and materialized views in [#146](https://github.com/osama784/schemamill/issues/146) ([ADR 0026](../adr/0026-catalog-comment-reads.md)), for primary-key, unique, check, foreign-key, and standalone-index comments in [#192](https://github.com/osama784/schemamill/issues/192) ([ADR 0028](../adr/0028-catalog-constraint-and-index-comments.md)), and for constraint-backed index comments in [#213](https://github.com/osama784/schemamill/issues/213) ([ADR 0030](../adr/0030-constraint-backed-index-comments-are-flagged.md)), where they are flagged rather than modeled. `comment-round-trip` and `comment-introspection` still carry `matches-import`; the `constraint-backed-index-comments` scene carries `flags`. Named-not-null comments now read through the `contype = 'n'` description and agree with the dump import on PostgreSQL 18 ([#147](https://github.com/osama784/schemamill/issues/147), [ADR 0038](../adr/0038-not-null-constraint-comments-travel-the-model.md)). Exclusion constraints' own comments are now modeled in [#90](https://github.com/osama784/schemamill/issues/90) ([ADR 0041](../adr/0041-exclusion-constraints-and-index-expressiveness-travel-the-model.md)); their backing-index comments remain flagged in both read paths ([#231](https://github.com/osama784/schemamill/issues/231), [ADR 0035](../adr/0035-exclusion-backing-index-comments-are-flagged.md)). Identity-sequence comments, view output-column comments, matview index comments, extension comments, and non-UTF-8 comments stay deferred by name in ADR 0028.
- **Grants, ownership, and security labels** — [#92](https://github.com/osama784/schemamill/issues/92).
- **View output columns, including their comments** — [#143](https://github.com/osama784/schemamill/issues/143); `COMMENT ON COLUMN <view>.<column>` is flagged today.
- **`COMMENT ON` deparse** — [#57](https://github.com/osama784/schemamill/issues/57).
- **The index-name collision-guard residual** — comment steps are not part of `renderSql`'s duplicate-name guard; an unnamed comment target and a differently shaped create could in principle share a server-form name.
- **Comment-aware canonicalization** — deliberately not introduced; resolution happens while the server name is stored, and adding a comment-aware strip would make the importer disagree with catalog reads.
- **The owned-sequence removal rule** — a comment on a sequence owned by a removed column follows the sequence; the existing owner-removal suppression decides whether that sequence survives, and no comment-specific rule is added.
