# 0031 — Exclusion diagnostic object names the table

**Date/Status:** 2026-11-21 · accepted

**Context:** [ADR 0016](./0016-catalog-constraint-canonicalization.md):17 pinned the catalog's whole-object exclusion-constraint skip as `kind: 'skip'`, `code: 'unsupported-statement'`, object `<schema>.<conname>`, and message `skipped exclusion constraint <schema>.<conname>`. That object names the constraint, not the table that owns it, which diverges from the object-naming convention settled by [#188](https://github.com/osama784/schemamill/issues/188) and from ADR 0016's own constraint grammar at :19 — a diagnostic attached to a model entity names the schema-qualified identity of the owning entity as its object and leaves the member detail (the constraint label) in the message, so a constraint finding names `<schema>.<table>`. The dump importer's exclusion wording already follows that convention and is unchanged by this correction. Accepted ADRs are immutable, so ADR 0016 stands as written and this ADR records the correction. [#237](https://github.com/osama784/schemamill/issues/237) settled the policy.

**Decision:** The catalog's exclusion skip now names the owning schema-qualified table as its object and carries the bare constraint label in the message: object `<schema>.<table>`, message `skipped exclusion constraint <conname>`. The owning table identity is already in scope in the table loop that nests the constraint loop, so the diagnostic uses it directly; no new catalog payload field or model shape is added. `kind: 'skip'` and `code: 'unsupported-statement'` are unchanged, as is every other finding path. The import side keeps its own distinct wording (`exclusion constraint <conname> on <schema>.<table>`) and is not changed here. The module contract in `catalog.ts` is updated to match, so the documented grammar and the emitted diagnostic agree.

**Consequences:** The catalog's whole-object exclusion skip now follows the same object-naming rule as the rest of its constraint diagnostics: the object identifies the owning table and the message names the constraint. Only the exact object and message strings of this one diagnostic change — the skip still fires for every exclusion constraint, because the model has no shape for it. The unit pins and the live-scene pin name the owning tables, and the scene comment describing the diagnostic reflects the table-object convention. The plan's #188 exception list no longer cites exclusion skips; `COMMENT ON` targets remain the named exception.

**Supersedes:** [ADR 0016](./0016-catalog-constraint-canonicalization.md):17's exclusion-skip object/message wording, for the exclusion-skip diagnostic only; the rest of ADR 0016 stands.
