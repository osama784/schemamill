# 0019 — Views and materialized views travel the model

**Date/Status:** 2026-10-27 · accepted

**Context:** `pg_dump` emits ordinary and materialized views, and the importer skipped both whole on the way to a model that held only `tables` and `sequences` ([#89](https://github.com/osama784/schemamill/issues/89), Slice B of the [import long-tail plan](../plans/import-long-tail.md)). Views are the first new object family since sequences, so the slice had to settle a model shape, an import envelope, plan placement, a change strategy, rendering, workspace compatibility, and live evidence in one pass. Relations, not query columns, are the unit the engine can own: a view has no modeled columns, types, or structure from which a query could be reconstructed. The accepted [ADR 0002](./0002-canonical-model.md), [0004](./0004-postgresql-only-dialect-seam.md), [0005](./0005-framework-free-core.md), [0009](./0009-render-refuses-duplicate-conventional-names.md), and [0010](./0010-workspace-container.md) stand as written; this ADR records the view-definition text exception and the workspace-format consequence.

**Decision:** `Model` gains a required `views` array, sorted by schema then name, and one `View` entity carries both kinds with a required `materialized` boolean plus an optional `checkOption` (`local` or `cascaded`; absent means none). Both kinds are relations in one namespace, share identity and ordering, and differ only in the rendered keyword and the change strategy, so one array and one diff group (`view-added`/`view-removed`/`view-changed`, after sequences) are enough; a change between the kinds is a `view-changed` on the `materialized` field, not a removal plus an addition. A workspace view with a check option and `materialized: true` fails closed as `invalid model`, because PostgreSQL has no such object.

The definition is opaque canonical text: import stores the body between the top-level `AS` and the statement terminator, minus a trailing `WITH [LOCAL|CASCADED] CHECK OPTION` or `WITH [NO] DATA`, whitespace-normalized and rendered verbatim on one line; core never parses or reconstructs it. This is the deliberate exception to the generated-SQL doctrine — a view's columns and structure are not modeled, so no structural reconstruction exists — and it puts a view body in the same class as a check expression or a default: owned text, compared as text. The spelling is the server's deparse (`pg_get_viewdef`), which can change across PostgreSQL majors; the model therefore pins no deparse text across versions. Live evidence compares imports produced by the same server (`crossImportChecks`), so a PostgreSQL 18 deparse spelling can never fail a PostgreSQL 16-authored expectation, and a hand-authored workspace definition is accepted as canonical.

A view's check option comes from the statement's clause or from a `check_option` reloption, the clause winning when both are stated. `WITH (...)` reloptions, view and matview column lists, a matview's access method and tablespace, `IF NOT EXISTS`, persistence, and the populated state are not modeled; every one that appears is flagged by name while the view still imports, so nothing dump-emitted is silently dropped. **The unlogged-form falsification:** libpg-query parses `CREATE UNLOGGED VIEW` and `CREATE UNLOGGED MATERIALIZED VIEW` because it exposes the raw grammar, but PostgreSQL rejects both at parse analysis (`views cannot be unlogged because they do not have storage`, `materialized views cannot be unlogged`), and `pg_dump` never dumps temporary objects, so the non-`p` persistence flags are defensive for hand-authored dumps only and are unit-pinned without live staging. **The recursive-view skip:** `CREATE RECURSIVE VIEW` parses into a view-named recursive CTE with synthetic locations and the raw body after `AS` omits that CTE, so importing it would store a definition that cannot be re-rendered; it is skipped and named, and `pg_dump` never emits the form because its deparsed `WITH RECURSIVE` body imports normally.

A changed plain view renders `CREATE OR REPLACE VIEW`, which preserves grants, ownership, comments, and dependent views while requiring PostgreSQL-compatible output columns. A changed materialized view, or any change between plain and materialized, renders `DROP … VIEW` plus `CREATE … VIEW … WITH NO DATA`, because a materialized view cannot be replaced and the recreate leaves it unpopulated and discards its indexes, grants, and dependents under `RESTRICT`. The consolidated common failing cases are (a) `CREATE OR REPLACE` when an existing output column is dropped, renamed, reordered, or type-changed; (b) adding a column before existing ones, since only append-only additions are compatible; (c) dropping a view that another view depends on before its dependents; (d) creating a view before a view it references; and (e) a kept view whose definition references a dropped sequence (global phase 9), table, or column. Each fails at apply with PostgreSQL's own `RESTRICT` or column-compatibility error; the view steps are transactional, so the transaction carrying them rolls back — the whole plan for a view-only migration — and there is no partial apply and no repair beyond fixing the model and re-planning. The two closing follow-ups are view output-column modeling (preflight compatibility for (a) and (b)) and a view dependency graph with topological ordering ((c) and (d)); (e) is the pre-existing well-formedness residual and is named, not closed by a follow-up.

View drops are global plan phase 4, before the table phases, so a removed view cannot block a table or column drop; view creates and then replaces are phase 6, after every table phase, so a view can reference newly created tables and columns. The three view steps are transactional and carry no table, column, sequence, or hazard payload; the hazard analyzer filters steps by kind, so view steps produce no hazards, and only its exhaustiveness cases grew.

Workspace `model.json` gains `views` after `sequences`, always serialized. An absent `views` key reads as `[]`, so model files written before this slice load unchanged, while `null`, a non-array, an unknown key, or a malformed view fails closed. No format version is introduced; versioning stays with [#54](https://github.com/osama784/schemamill/issues/54). The scope boundaries are named: view comments, grants, ownership, and security labels ([#87](https://github.com/osama784/schemamill/issues/87) and later); catalog introspection and `matches-import` for views ([#71](https://github.com/osama784/schemamill/issues/71)); view reloptions, persistence, columns, matview indexes, tablespace and access method, populated state and `REFRESH`, the matview-rewrite hazard, `ALTER VIEW`, `CREATE TABLE AS`, recursive-view import, and view dependency ordering. No new dependency is introduced; libpg-query stays in `@schemamill/postgres`.

**Consequences:** The canonical model now has three arrays — tables, sequences, and views — and a dump's plain and materialized views round-trip through import, diff, plan, and render with a check option and a kind change. The workspace format grows a `views` section that older files need not carry; the CLI prints view changes and steps; the postgres `views.sql` golden and the CLI `views` scene pin the rendered bytes; and the gated `view-round-trip` scene proves the round trip with server-derived imports deep-equal instead of pinned deparse text. View steps produce no hazards, and a materialized `replace-view` plan is refused with `RenderRefusalError`. The deferrals above stay visible in the [plan](../plans/views.md), and ADR 0002, 0004, 0005, 0009, and 0010 are untouched.

**Deferred:** View reloptions modeling; persistence modeling for views and matviews (defensive flags only); view and matview column lists and output columns; matview indexes; matview tablespace and access method, including the dump-side `SET` GUCs that steer them and stay outside the model; populated state and `REFRESH`; a view dependency graph and topological drop/create ordering; dependency-aware hazards; the matview rewrite hazard; comments, grants, ownership, and security labels for views; catalog introspection parity and `matches-import`; workspace format versioning ([#54](https://github.com/osama784/schemamill/issues/54)); recursive-view import; `ALTER VIEW`; `CREATE TABLE AS`; and view/table name-collision guards.
