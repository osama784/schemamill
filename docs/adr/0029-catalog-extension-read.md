# 0029 — Catalog extension read

**Date/Status:** 2026-11-15 · accepted

**Context:** [#91](https://github.com/osama784/schemamill/issues/91) gave the model an `extensions` array and made the dump importer, diff, plan, renderer, CLI, and `extension-round-trip` carry name, install schema, and comment, but it left the live catalog read returning `extensions: []`. [ADR 0022](./0022-extensions-travel-the-model.md):17 recorded the gap as "The catalog is deferred", and [ADR 0028](./0028-catalog-constraint-and-index-comments.md):19 still listed extension reads and comments as remaining out. Both ADRs are accepted and stay unedited; this ADR is the record for [#150](https://github.com/osama784/schemamill/issues/150). The read had to settle which catalog tables supply the row, how the payload carries an OID that the model will never hold, which installed extensions are the model's, how the rows order, what a duplicate name means, and how a server comment's absent state is represented.

**Decision:** The catalog read gains a ninth required `extensions` payload section, read in the same single `psql -c` batch as the other eight. `pg_extension` joins `pg_namespace` on `extnamespace` for the install schema, and the comment comes from `pg_catalog.obj_description(extension.oid, 'pg_extension')`; the row is `extension.oid::text AS oid`, `extension.extname AS name`, `namespace.nspname AS schema`, and the description. `oid::text` is deliberate: PostgreSQL emits an OID through `oidout` as canonical decimal text and `json_categorize_type` has no `OIDOID` case, so a JSON number would lose the exact spelling. The SQL selects every installed extension, built-ins included, and applies no namespace exclusion, because extensions are not schema objects in the `pg_catalog`/`pg_%` sense; only the mapper owns the built-in policy.

The mapper excludes built-ins with `pg_dump`'s rule. `pg_dump` marks an extension dumpable iff `oid > g_last_builtin_oid`, where `g_last_builtin_oid = FirstNormalObjectId - 1 = 16383` (`pg_dump.c` REL_13:1830, REL_16:2041, REL_18:2242; `transam.h` defines `FirstNormalObjectId = 16384`), so the mapper keeps a row only when `BigInt(row.oid) >= 16384n`. The predicate lives in the mapper rather than the SQL so the riskiest rule is unit-falsifiable at its exact boundary, the same division that already puts `relkind`, `relpersistence`, and `attidentity` policy in the mapper. Before filtering, every row is parsed and a repeated name is a contract throw, `catalog payload: duplicate extension "<name>"`: one row per extension is a catalog invariant, and the check covers duplicate built-ins too, so drift cannot disappear behind the filter. The surviving rows sort by name only through a local `compareExtensionRows` mirroring the model's `compareExtensions` and the importer's order; SQL's `ORDER BY extension.extname` only stabilizes the payload and is not authoritative. Each row then maps to `{ name, schema, comment? }`; the OID never reaches the model.

The comment follows the model's comments contract exactly. A null description and the empty string both mean absent and omit the model key, because PostgreSQL deletes a comment on `COMMENT … IS ''` just as it does on `IS NULL`, and dump import already clears on `IS ''`; a description containing `U+0000` throws a contract error naming the payload path, because PostgreSQL text cannot hold one and the payload is untrusted. The older catalog comment families keep their pre-existing behavior — they attach `''` and do not reject NUL — which is a named residual below rather than a change in this slice.

**Why not a name list, and why not `pg_depend`.** An `extname <> 'plpgsql'` rule diverges from a dump in both directions. `pg_dump` itself notes that a dropped and recreated `plpgsql` gets an OID greater than `g_last_builtin_oid` and is then dumped (`pg_dump.c` REL_16:10586-10591), so a name list would exclude an extension the dump emits; conversely, any future or initdb-installed extension below the boundary would be excluded by a dump and kept by a name list. The OID predicate is the only rule that matches a dump's behavior for every row. A `pg_depend` rule with `deptype = 'e'` describes the member objects that belong to an extension, not which extensions `pg_dump` emits — `getExtensions` never reads `pg_depend` — so it answers a different question. Filtering by install schema (`pg_catalog`) is also rejected: it happens to hide `plpgsql` but would hide a user extension deliberately installed in `pg_catalog`, which a dump would emit.

**Consequences:** A live import now returns the installed extensions a dump would recreate, with their install schema and comment, in name-only order. The existing `extension-round-trip` scene gains `introspection: { assert: 'matches-import' }`; it already moves `hstore` into the non-public `hs2`, installs `pgcrypto` in `public`, and removes `citext`, so the assertion proves the name, schema, and comment mapping against the applied dump's import, and the ambient `plpgsql` in the same database proves the built-in exclusion. **No new scene** was added. Unit tests pin the name-only ordering against a schema-first fixture, the boundary at 16383/16384/16385, the absent and NUL comment paths, the duplicate throw, and every malformed row. [The extensions plan](../plans/extensions.md) carries the slice's evidence.

**Invisible and deferred by name.** Extension members stay unmodeled (the [ADR 0018](./0018-catalog-sequences-and-identity-columns.md) residual), and the read does not filter member objects out of the other sections. `extversion`, `extrelocatable`, and `extconfig` remain unread and unmodeled; `-e`/`--exclude-extension` remains out of scope, so the catalog always reports every dumpable extension rather than a filtered set. The OID rule carries a standalone-mode edge: a backend run in single-user mode allocates OIDs from the initdb range until the first postmaster start (`GetNewObjectId` in `varsup.c`), so an extension installed there can sit below the boundary and be treated as built-in — exactly as `pg_dump` treats it, because the rule is dump congruence, not provenance. The older catalog comment families still attach `''` and accept NUL in server-unreachable states, while the extension section normalizes empty to absent and throws on NUL. The views section still sorts and maps without a duplicate-name throw; the extension read follows the tables, columns, indexes, constraints, and sequences majority and throws instead. NUL postures differ by path by design: dump import flags a NUL-carrying comment, the catalog throws on one, and the workspace fails closed. ADR 0022 and ADR 0028 remain unedited; this ADR and the plan edit supersede their deferral without rewriting the accepted record.
