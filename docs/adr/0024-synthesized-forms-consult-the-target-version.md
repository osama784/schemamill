# 0024 — Synthesized forms consult the target version

**Date/Status:** 2026-11-01 · accepted

**Context:** `renderSql(plan)` took only the plan, and two renderer-synthesized statements were emitted unconditionally: `SET STORAGE DEFAULT` (PostgreSQL 16) and `SET COMPRESSION default` (PostgreSQL 14). A plan at the documented PostgreSQL 13 floor could therefore render SQL PostgreSQL 13 rejects, silently. [ADR 0012](./0012-constraint-attributes-travel-the-model.md) decided that PostgreSQL 18-only syntax renders as declared "because the source carried the declaration", and [ADR 0015](./0015-column-attributes-travel-the-model.md) already stated the two floors — "The version floors are stated, not negotiated: `SET STORAGE DEFAULT` needs PostgreSQL 16 and `SET COMPRESSION` needs 14" — but no code enforced them; the 13–15 storage-removal case was a named residual only. [Core-domain hard problem #5](../domain/core-domain.md) asks three things of version handling: live work detects the server version, offline work states a target, and generation answers for that target. The live half stays with [#57](https://github.com/osama784/schemamill/issues/57); the offline half needed a durable decision ([#141](https://github.com/osama784/schemamill/issues/141)).

**Decision:** `renderSql(plan, options?: RenderOptions)` accepts `RenderOptions.targetVersion`, the PostgreSQL major the SQL is generated for. It defaults to `MIN_TARGET_VERSION` (13, the documented floor) and accepts any integer at or above it; `MAX_TARGET_VERSION` (18) is the newest form the renderer knows, and a newer target is accepted and behaves like 18, because every synthesized form is then available and a future server supports it. A target that is not an integer or is below 13 is a caller bug and throws a plain `Error`, not a refusal.

Only the renderer's own synthesized forms consult the target: `SET STORAGE DEFAULT` refuses below 16 and `SET COMPRESSION default` below 14. The gate sits in the emitter that decides the value, so it cannot drift from the emission logic and the first offending statement in plan order reports. Both throw `RenderRefusalError` with the pinned one-line shape `refusing to render for PostgreSQL <target>: <form> on <table> column <column> needs PostgreSQL <floor> or newer`, where the table is schema-qualified and both identifiers use SQL's minimal quoting. The message is library-level and never names a CLI flag.

Declarations the model carries render as declared at every target: an explicit storage letter or compression method, a named `NOT NULL`, and `NOT ENFORCED`. The model carried the declaration, and validating it against the target would re-litigate ADR 0012; that residual is named below. The plan stays version-free: one plan renders for several targets, snapshot comparison and every plan literal stay unchanged, and the `SqlRenderer` `render(plan)` seam is untouched — `renderSql(plan, options?)` still satisfies it and `sqlRenderer` keeps the default 13. The CLI adds `plan --target-version <major>`, restricted to the declared 13–18 span and validated before any filesystem access as a usage error; `export` renders creates only and `compare` renders nothing, so neither takes a flag in v1. The live harness renders every scene for the server under test and passes the server major to the plan-check probes.

**Consequences:** A plan that resets storage or compression no longer renders by default: it refuses until the target declares 16 or 14 respectively. That is the deliberate behavior change — loud, named in the message and in `plan --help`, and recorded in the changelog — and it makes the documented PostgreSQL 13 floor true rather than aspirational. A target above 18 is accepted and trivially satisfied.

Declaration validation against the target is a named residual, not a silent guarantee. The per-form consequences when a target sits below a declaration's floor are:

| Declaration | On a target below its floor | Loudness |
|---|---|---|
| PostgreSQL 18 named `NOT NULL` (inline or `ADD CONSTRAINT … NOT NULL`) | 13–17 accept the inline form and discard the name — no `pg_constraint` row, so a later `COMMENT ON CONSTRAINT` fails | **silent** |
| `NOT ENFORCED` on a check or foreign key | 13–17 reject the statement | loud syntax error at apply |
| explicit `COMPRESSION` method | 13 rejects the statement | loud syntax error at apply |
| explicit `STORAGE` letter | valid on all of 13–18 | harmless |

The silent row is the named cost of the ADR 0012 fence: a target below 18 with a named `NOT NULL` declaration renders as declared and its name is lost on apply. Fixing that gap needs its own slice and ADR, and the [target-version plan](../plans/target-version.md) carries the table as its body.

The oldest-major live leg is a recorded deviation: the development host has only PostgreSQL 16.15 and CI only 18, with no 13/14/15 package available and no container runtime. The 13 target's behavior is a pre-SQL refusal with no PostgreSQL 13-specific SQL to apply, so the unit boundary tests and the 13-floor sweep across the 14 non-reset goldens carry that evidence; a PostgreSQL 13 CI job is proposed at bookkeeping. `export` and `compare` take no target flag in v1 — export's creates can never emit a reset, and compare renders nothing — so those flags wait for their first version-sensitive form or for the declaration-validation follow-up.

**Amendment by correction, not supersession.** ADR 0016 recorded the precedent: "Accepted ADRs are immutable, so ADR 0014 stands as written and this paragraph is the correction." In the same way, ADR 0012's sentence that "the renderer negotiates no server version, because the source carried the declaration" and ADR 0015's that "the renderer states as declared and negotiates no server version" are narrowed to **declarations**. Declarations still render as declared; only renderer-synthesized reset forms consult the declared target. ADR 0012 and ADR 0015 remain accepted and unedited, and this ADR is the record for synthesized forms.
