# 0030 — Constraint-backed index comments are flagged

**Date/Status:** 2026-11-17 · accepted

**Context:** The model carries `comment?: string` on primary keys, unique, check, and foreign-key constraints, and standalone indexes ([ADR 0021](./0021-comments-travel-the-model.md)), and the catalog read returns those descriptions ([ADR 0028](./0028-catalog-constraint-and-index-comments.md)) — but it has no `Index` slot for the index a primary key or unique constraint owns. Before this slice the two read paths disagreed about that index's own `pg_class` description. The dump importer's hand-authored `ADD CONSTRAINT … USING INDEX` splice read the consumed index's comment and copied it onto the constraint it built, while a plain `pg_dump` flow's late `COMMENT ON INDEX` found no draft index and flagged `dropped comment from <schema>.<index>`. The catalog excluded every constraint-backed index through the `conindid` join and read only `obj_description(c.oid, 'pg_constraint')`, so it was silent where the plain import flagged. [ADR 0028](./0028-catalog-constraint-and-index-comments.md):15 recorded the divergence as a named residual and :19 closed the catalog slice without a diagnostic for the class; both are accepted and stay unedited. [#213](https://github.com/osama784/schemamill/issues/213) settled the policy.

A live probe on PostgreSQL 16.2 established the facts the policy rests on. The two description slots are independent: `obj_description(ic.oid, 'pg_class')` on the backing relation and `obj_description(c.oid, 'pg_constraint')` on the constraint each return their own text, so a commented index and a commented constraint coexist on one key. `pg_dump --schema-only` emits both forms — `COMMENT ON CONSTRAINT … ON …` and `COMMENT ON INDEX …` — after the `ALTER TABLE ONLY … ADD CONSTRAINT` statements. A database built with `USING INDEX` dumps with no `USING INDEX` and no source index name: PostgreSQL renames the consumed index to the constraint's name at apply time, and the dump carries `COMMENT ON INDEX` on that post-rename name. `COMMENT ON INDEX` on a constraint-backed index is legal and silent. One join trap is load-bearing: for a foreign key, `conindid` names an index on the *referenced* table, so any join to a backing relation must be guarded to `contype IN ('p', 'u', 'x')` — or, in the constraints read, to a `CASE` on `contype = 'u'` — or an unrelated index's comment becomes a false flag.

**Decision:** Both read paths flag a constraint-backed index's comment and neither copies it. The escape hatch the ruling allowed — keep the `USING INDEX` copy if it yields the same observable outcome — is falsified. Applied to a server, a `USING INDEX` database dumps as a plain constraint plus `COMMENT ON INDEX` on the renamed backing index, and the catalog reads the constraint's own `pg_constraint` description, which the copy never wrote (it stored the text on the model's constraint). Re-importing the dump of a copy-built model therefore loses the copied constraint comment and flags the index comment: the copy cannot reproduce itself across its own round-trip, so it cannot satisfy the one-database-one-outcome bar. The copy is removed from both splice functions; a consumed index's comment is dropped and flagged whenever it carries one, with no comparison against the retained constraint's text. "Identical text stays silent" is retired for consumed comments: it belonged to the copy's lossless case, and the plain dump flow flags a late `COMMENT ON INDEX` regardless of what the constraint says.

The flag names the object the statement leaves behind, and the branch decides which name that is. When the attachment applies, PostgreSQL renames the consumed index to the built constraint's name (`constraint.conname ?? index.name`), so the flag names `<schema>.<built name>` — the name a dump and the catalog will use for the same database. When the declaration is deduplicated onto an equal retained constraint or rejected as an additional primary key, the server rejects the statement, no rename happens, and the source index keeps its name, so the flag names `<schema>.<indexname>`. A late `COMMENT ON INDEX` after consumption already names the dump's name and keeps its generic flag. One residual stays by name: an auto-generated constraint name in a `USING INDEX` attach is not mirrored by the simulator, so that success-path edge names the model's name; source-`USING INDEX`-name preservation in the diagnostic is likewise out.

The catalog reads the backing index on the existing primary-key and constraint rows rather than adding a payload section. `primaryKeys` gains a `LEFT JOIN pg_class AS backing_relation ON backing_relation.oid = key_constraint.conindid`; its `contype = 'p'` filter already guards the join. `constraints` reuses its `backing_index` row and joins the same `pg_class` relation, selecting the relation name and description through `CASE WHEN c.contype = 'u' THEN … END`, which is the guard for the foreign-key trap and the exclusion, check, and foreign-key kinds. `PrimaryKeyRow` gains a required, non-nullable `backingIndexName: string` — a primary key always has one — and a nullable `backingIndexComment: string | null`. `ConstraintRow` gains a present-but-nullable `backingIndexName: string | null` and a nullable `backingIndexComment: string | null`; `validateConstraintRow` requires `backingIndexName` for `unique` and requires both fields absent for `check`, `foreign-key`, and `exclusion`, while `backingIndexComment` stays nullable for every kind. The primary-key path needs no kind matrix. Primary-key rows repeat per key column, so the grouping pass requires them to agree on the new fields exactly as on their other attributes. The fields are allow-listed in `expectFields` and parsed by `expectString`/`expectNullableString`; null means no comment, and the model omits the key. **The model is unchanged** — there is still no `Index` slot for a constraint-backed index — and so are diff, plan, and render.

Emission belongs to the index phase. The mapper collects each table's standalone-index diagnostics and appends one flag per non-null `backingIndexComment` — from the primary-key mapping and from each `unique` row — with the import's exact grammar: `{ kind: 'flag', code: 'unsupported-attribute', object: '<schema>.<backingIndexName>', message: 'dropped comment from <schema>.<backingIndexName>' }` and no `position`. The combined list sorts by stored name and is pushed after the constraint findings, so the documented order reads "constraint findings in stored `conname` order, index findings — standalone-index diagnostics and dropped comments on constraint-backed indexes — after them in stored-name order". Consumed indexes never appear as standalone rows, so the per-table index-phase names are unique and no tiebreak is reachable.

A pre-fix workspace needs no data migration; re-import is the repair. A model written by the old import carries the copied text in the constraint's `comment`; re-importing the same database returns the constraint without it, so `diff` reports a comment change with an absent `after` and the plan renders `COMMENT ON CONSTRAINT … IS NULL`. That step is a no-op against a database whose `pg_constraint` description is empty — precisely the `USING INDEX` shape — and it removes the phantom text from the workspace. Reverting the slice reverses the shape: re-import copies the backing index's comment back onto the constraint and stops flagging it.

**Consequences:** An import and a catalog read of an identical database now produce the same observable outcome — the same `dropped comment from <schema>.<index>` flag on the same index-named object, and the same model with no comment on the constraint — except the named auto-generated-constraint-name residual. Both read paths are pinned: import units cover the applied and dedupe/reject branches and the object-name split, catalog units cover the primary-key and unique reads, the ordering merge, and the row contract, and the `constraint-backed-index-comments` live scene asserts `flags` (not `matches-import`, since both paths now report a diagnostic) with a cross-import equality check. The plain dump flow's late flag is unchanged, and a later `COMMENT ON CONSTRAINT` still attaches normally.

**Deferred:** Comments on exclusion constraints, both the constraint's and its backing index's — the constraint is skipped whole. Comments on invalid, not-ready, or out-of-envelope indexes. Partitioned and child tables and their indexes; matview indexes. A model slot for backing index comments (this ADR deliberately keeps them unrepresentable and flagged). Live coverage of the hand-authored `USING INDEX` splice path — `pg_dump` never emits `USING INDEX`, so it stays unit-only. Catalog diagnostics surfaced outside the live harness — the CLI does not print them. PostgreSQL 18 named not-null constraint comments ([ADR 0028](./0028-catalog-constraint-and-index-comments.md)). Comments on tables the catalog skips whole. The auto-generated-constraint-name edge in `USING INDEX` attaches, and source-`USING INDEX`-name preservation in the diagnostic.

**Supersedes:** [ADR 0028](./0028-catalog-constraint-and-index-comments.md):15's "the catalog is silent" and :19's "a catalog-side diagnostic for any of these classes is not introduced", for the primary-key and unique backing-index class only; the rest of ADR 0028's scope stands. [ADR 0021](./0021-comments-travel-the-model.md) is not superseded: it never states the copy, and its `:17` "flagged, never silent" wording already aligns with this policy. [ADR 0016](./0016-catalog-constraint-canonicalization.md):9's `USING INDEX` provenance residual is untouched — this ADR changes no structural rule and adds no provenance recovery.
