# 0032 — Materialized-view indexes travel the model

**Date/Status:** 2026-11-22 · accepted

**Context:** A dump's materialized-view indexes arrive as ordinary post-data `CREATE [UNIQUE] INDEX … ON <matview>` statements, and PostgreSQL records an index's link to its parent as `DEPENDENCY_AUTO`, so dropping the matview auto-drops its indexes. The model had no slot for them: the importer resolved every such statement against table drafts only and skipped it as a table that was not imported, so a real access path was lost on import and silently destroyed on a rewrite. Table indexes already round-trip under [ADR 0008](./0008-index-concurrency-is-declaration-metadata.md) and [ADR 0014](./0014-catalog-index-canonicalization.md); an index on a materialized view is the same `Index` shape with a different owner. [ADR 0019](./0019-views-and-materialized-views-travel-the-model.md) shipped views and materialized views and named matview indexes as deferred; [ADR 0028](./0028-catalog-constraint-and-index-comments.md) and [ADR 0030](./0030-constraint-backed-index-comments-are-flagged.md) defer their comments. Accepted ADRs are immutable, so this ADR records the index contract without editing them. [#175](https://github.com/osama784/schemamill/issues/175) and the [matview-indexes plan](../plans/matview-indexes.md) drove the slice.

**Decision:** `View` gains an optional `indexes: readonly Index[]`, present only on materialized views. Import omits the key when there are none, `serializeView` writes it only when non-empty, and every reader treats absence as no indexes with `view.indexes ?? []`, so pre-slice workspace bytes and the existing index-less view assertions stay unchanged. An ordinary view carrying a non-empty array fails closed at the workspace boundary. No second index type, no top-level `Model.indexes`, and no phantom `Table` are introduced; the `Index` shape, its name-or-structure identity, its generated-name canonicalization, and its `concurrently` apply metadata are exactly the table-index ones.

The owner travels as `IndexOwner = { kind: 'table', table } | { kind: 'materialized-view', view }` on the index change kinds — `view-index-added`, `view-index-removed`, and `view-index-changed` join the table-index group — and on the index step kinds. The discriminant drives phase placement and the duplicate-name guard key; table-owned steps keep their existing identity, ordering, phases, and bytes. `CommentTarget` stays table-only, so matview index comments are not threaded through comment dedupe and [ADR 0021](./0021-comments-travel-the-model.md) is untouched here.

Import resolves the owner in table drafts first, then view drafts, through the same minimal envelope and the same `synthesizedIndexName`/`indexStructureKey` canonicalization; a repeated `CREATE MATERIALIZED VIEW` clears the earlier indexes. Two named diagnostics keep their exact wording: an index on an ordinary view is skipped with `object = <schema>.<index>` and message `skipped CREATE INDEX <schema>.<index> (indexes are not supported on a plain view)` — a pre-apply diagnostic, not a copy of server text — while an index whose owner resolves to neither draft keeps the unchanged `skipped CREATE INDEX <object> (table not imported)` skip. Both name the index in `object` when the source names it, following the [#188](https://github.com/osama784/schemamill/issues/188) object-naming convention that [ADR 0031](./0031-exclusion-diagnostic-object-names-the-table.md) records for catalog skips without changing import wording.

A recreated matview owns every index of its identity. `plan()` computes the recreated set from `view-changed` changes where either side is materialized and filters the diff's per-index changes for those identities **before** the apply loop, leaving the exported `applyChange(application, change)` signature and its direct callers untouched. An added view decomposes into its `create-view` plus one create step per target index; a recreated view emits baseline index drops, the view drop and create, and one create step per target index; a kept matview's added, removed, or changed index emits its own drop or create. View-owned drops go in a new phase-5 `viewIndexDrops` bucket immediately ahead of `application.viewDrops`; view-owned creates go in a new phase-7 `viewIndexCreates` bucket immediately after `application.viewReplaces` — never in `application.indexCreates`, which assembles before `viewCreates` and would render `CREATE INDEX … ON <matview>` before the matview exists. A removed view emits no index drops. A concurrent matview index keeps its non-transactional classification and stands alone, correctly grouped only because `viewIndexCreates` follows `viewCreates`. Step, phase, and transactional counts do not move.

`DEPENDENCY_AUTO` means `DROP MATERIALIZED VIEW` auto-drops its indexes under `RESTRICT`, so the plan emits no separate index drops for a removed view. The gated `matview-index-round-trip` scene proves the physical fact on a distinctly named probe matview: after the migration the probe is gone and its index rows are gone, unambiguous against the rewrite target. Reverting the slice removes the model slot and the import path; a workspace written by the new importer carries an `indexes` key on matviews that an older binary rejects as unknown ([ADR 0010](./0010-workspace-container.md)) — the same accepted backward-compatibility cost as `views` and `extensions`, with no format version introduced ([#54](https://github.com/osama784/schemamill/issues/54)).

**Consequences:** Matview indexes now round-trip through import, diff, plan, render, workspace, CLI, goldens, and the live suite with the same identity and canonicalization as table indexes; a rewrite recreates all target indexes instead of losing them silently. Table-index behavior is byte-unchanged. The named residual is **partial apply**: a recreate and its index creates are separate steps, and a `CREATE INDEX CONCURRENTLY` stands outside a transaction, so a failed concurrent create after the committed recreate leaves an unpopulated, un-indexed matview — the plan carries no hazard annotation for it in this slice. The catalog read stays table-scoped (`relkind = 'r'`), so a live-database import still loses matview indexes without a diagnostic until catalog parity lands; `COMMENT ON INDEX` on a matview index is still unresolvable because comment targets remain table-only.

**Deferred:** Catalog introspection parity for matview indexes ([#71](https://github.com/osama784/schemamill/issues/71)); matview index comments ([#146](https://github.com/osama784/schemamill/issues/146)); a schema-wide duplicate-index-name guard ([#102](https://github.com/osama784/schemamill/issues/102)), the guard staying owner-scoped so a table/matview name collision remains the named residual; view dependency and topological ordering ([#143](https://github.com/osama784/schemamill/issues/143)); the matview rewrite hazard for data, grants, and dependents ([#58](https://github.com/osama784/schemamill/issues/58)); matview reloptions, tablespace, and access method; populated state and `REFRESH`; expression, partial, and `INCLUDE` indexes ([#90](https://github.com/osama784/schemamill/issues/90)); and view/table name-collision guards ([ADR 0019](./0019-views-and-materialized-views-travel-the-model.md)). The partial-apply residual above is named, not annotated, in this slice.

**Supersedes:** [ADR 0019](./0019-views-and-materialized-views-travel-the-model.md)'s `Deferred` item "matview indexes" only — now delivered by this ADR; the rest of ADR 0019 stands, and ADRs 0021, 0026, 0028, 0030, and 0031 are untouched.
