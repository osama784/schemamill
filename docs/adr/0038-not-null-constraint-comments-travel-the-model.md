# 0038 — Not-null constraint comments travel the model

**Date/Status:** 2026-11-25 · accepted

**Context:** Since [ADR 0021](./0021-comments-travel-the-model.md) the model has carried `comment` on tables, columns, sequences, views, materialized views, primary keys, unique/check/foreign-key constraints, standalone indexes, and extensions — but PostgreSQL 18 also permits a name on a not-null constraint (`CONSTRAINT <name> NOT NULL`) and therefore a `COMMENT ON CONSTRAINT <name> ON <table>`. [ADR 0012](./0012-constraint-attributes-travel-the-model.md):7 records the durable shape: there is no separate not-null constraint object; a not-null name is a `Column` attribute, and `Column.comment` is `COMMENT ON COLUMN`, not a comment on the not-null constraint. Before this decision both read paths dropped that text: the dump importer flagged `dropped comment on a not-null constraint from <schema>.<table>.<constraint>`, and the catalog read selected no description for `contype = 'n'` rows ([ADR 0028](./0028-catalog-constraint-and-index-comments.md):19 named it out). The generated-name detail was the crux: `pg_dump` 18 keeps a generated `<table>_<column>_not_null` name when it is commented, while canonicalization strips that formula to unnamed so a model-declared unnamed not-null round-trips ([ADR 0013](./0013-generated-names-and-omitted-declarations-round-trip.md):9). [#147](https://github.com/osama784/schemamill/issues/147) chartered the choice between (1) promoting the named not-null fact to an entity with its own comment slot and (2) attaching a comment surface to the column's not-null fact. This ADR records option 2.

**Decision:** `Column.notNullComment?: string` carries the text verbatim, valid whenever `notNull: true` — **not** only when `notNullName` is present, because the primary generated-name case strips the name to absent while retaining the comment. Like every other comment it is absent when there is no text, rejects `''` and NUL at the workspace boundary, and stays out of structural equality, `ColumnAttributes`, and every field-change union. It rides exclusively through `comment-changed` and a new `not-null` `CommentTarget` variant that carries the **whole `Column`** (so the renderer can resolve its server name), then through the single transactional `comment` step into terminal phase 12. It is deliberately not a `ColumnFieldChange`: a field-only change decomposes into `drop-not-null`/`add-not-null` and would drop the comment with the fact. Diff emits it beside the existing column comment; not-null drop/add and column recreate re-assert it, with one step per target after the sort; column copies strip it so change payloads carry no stale text.

A comment target need not promote the fact it describes. Option 1 — a `NotNullConstraint` entity — would reverse ADR 0012's "no separate not-null constraint object", duplicate the authoritative not-null fact on the column, and force a structural identity for something the model already expresses as an attribute of a column. Option 2 keeps the fact where it has always lived and adds only an eleventh `CommentTarget` variant, so the existing "ten modeled entities" and "seven `COMMENT ON` forms" prose stays true; no new entity and no eighth form is introduced. The attribute is the single source of truth for the fact; the comment is descriptive text on the same column, not a second carrier of it.

**Generated names and canonicalization.** Import resolves the comment against the stored server name while the drafts still carry it — using `synthesizedNotNullName` as the fallback for a generated name the source stated — stores `notNullComment` on the column, then strips the generated name **unconditionally**. Canonicalization stays comment-blind: a name matching the server formula never survives because it happens to carry a comment, since a comment-aware strip would make the dump importer disagree with the catalog read. The renderer resolves the target with `column.notNullName ?? synthesizedNotNullName(table.name, column.name)` — an explicitly named not-null is modeled and must be named as stored, while a stripped generated name is re-synthesized so the statement finds the constraint the server kept. A collision-suffixed name stays named and comments resolve against it directly; the ADR 0013:9 collision boundary for a suffixed generated name carrying a comment remains named as a residual.

**Catalog congruence is in scope.** The `contype = 'n'` read selects `obj_description(not_null_constraint.oid, 'pg_constraint')`, carries it as a required nullable row field parsed fail-closed, omits the model key on null, and preserves the comment through conventional-name canonicalization; null, empty text, `NOT VALID`, and `NO INHERIT` keep their existing handling. The PostgreSQL 18 `not-null-constraint-names` live scene puts `notNullComment` on its target column and asserts `matches-import` — zero diagnostics, empty diff, deep-equal model — so a dump import and a live introspection of the same database agree. `comment-round-trip` stays at the PostgreSQL 13 floor and cites the PostgreSQL 18 scene for named-not-null comment coverage; no per-case version gate and no new scene are added. With no PostgreSQL 18 server available locally, the live proof is CI-only; the unit pins (import retention, catalog row, diff/plan/render emission, workspace validation) carry the local evidence.

**Target version.** A not-null comment follows [ADR 0024](./0024-synthesized-forms-consult-the-target-version.md)'s declaration rule: a `notNullComment` plan rendered at `--target-version 13` (or any target below 18) still emits `COMMENT ON CONSTRAINT … ON …`, with no refusal. The renderer synthesizes no version-gated form here — it only names the object the declaration names — so there is nothing to consult the target about. The ADR 0024 table's named cost still applies at apply time: PostgreSQL 13–17 discard a named `NOT NULL`, so a later comment statement has no constraint to attach to. That is recorded, not re-litigated here, and the behavior is pinned at the 13 floor in `render.test.ts`.

**Compatibility and rollback.** The new `notNullComment` workspace key is additive; an older binary fails closed on it ([ADR 0010](./0010-workspace-container.md)), while a pre-fix workspace or a pre-fix import that carries the old flag needs no data migration — re-import is the repair, and reverting the slice restores the flag and the dropped comment. No format version, version floor, model entity, or `CommentTarget` form changes; existing goldens and the CLI's human output for uncommented not-null facts stay byte-identical. Studio consumption stays deferred: no server surface reads `CommentTarget` today.

**Consequences:** A `COMMENT ON CONSTRAINT` on a PostgreSQL 18 named not-null — explicit or generated — now imports onto the column with no flag while the generated name still strips, travels as its own terminal comment change, catalogs back to the same model, and renders back as the same statement. Unnamed not-null facts without a comment and the `NOT VALID`/`NO INHERIT` flag paths are unchanged. The public core type changes, so downstream exhaustive switches must map the new variant; core, postgres, CLI, goldens, and the gated PG18 scene carry the evidence. Deferred by name: studio consumption ([#83](https://github.com/osama784/schemamill/issues/83)), `COMMENT ON` deparse ([#57](https://github.com/osama784/schemamill/issues/57)), an exclusion constraint's own comment ([#90](https://github.com/osama784/schemamill/issues/90)), view output-column comments ([#143](https://github.com/osama784/schemamill/issues/143)), non-UTF-8 comments, declaration validation against the declared target (ADR 0024's residual), and the suffixed-generated-name collision boundary recorded above.
