# 0037 — The import fidelity report aggregates diagnostics

**Date/Status:** 2026-11-25 · accepted

**Context:** The [slice plan](../plans/import-fidelity-report.md) asks for a deterministic, human-reviewable report over one DDL dump so a human can judge round-trip fidelity before accepting the resulting model. The importer already emits every finding through one channel — the `Diagnostic` union (`skip`, `flag`, `error`) with stable codes, messages, source positions, and a schema-qualified owning object on skips and flags — and a parse failure arrives as an `error` diagnostic rather than a thrown exception. What was missing is one document that presents every finding the importer emitted for a dump, with no second collection path and no re-derivation from the model. The plan's "family and reason" wording needs an explicit mapping: `family` is not an owned headword in [CONTEXT.md](../../CONTEXT.md), and the codebase uses the word in two established senses.

**Decision:** `schemamill report <dump>` takes one positional (a dump path, or `-` for stdin), carries no flags in v1, and writes one human-readable document to stdout. The document is one line per finding — `kind code<TAB>object<TAB>message (line:column)` — with the object omitted for error rows, groups separated by a blank line, no header, no count line, and exactly `No findings.\n` for a clean dump. Positions are source-relative, so the bytes carry no dump path, workspace root, timestamp, random identifier, environment read, or locale-dependent sort; the same dump renders byte-identically at any path. There is no envelope, no `schemaVersion`, and no machine projection: this is a text document for a human reader, with versioning left to [ADR 0033](./0033-json-output-envelope.md) should a machine consumer ever appear.

The plan's "family and reason" means the diagnostic's `(kind, code)`, which yields five fixed groups in canonical order: `skip/unsupported-statement`, `skip/psql-meta-command`, `skip/copy-data`, `flag/unsupported-attribute`, `error/parse-failure`. The evidence is the shipped Diagnostic DTO contract in [docs/json-output.md](../json-output.md) at `:177-178`: `kind` is documented as "The finding's severity/family" and `code` as "Stable machine label; human stderr deliberately omits it." Each code belongs to exactly one kind, so the pair is unambiguous, and the codes are the importer's own stable labels. The competing codebase sense of "family" — the modeled entity families counted in [docs/json-output.md](../json-output.md) at `:52` and in the four-family model counts in [CHANGELOG.md](../../CHANGELOG.md) — is explicitly dismissed: an `error` diagnostic carries no `object` and a statement-level `skip` has no model family, so grouping by modeled entity cannot represent every finding. Grouping by message also fragments one stable template across object names. Nothing in `CONTEXT.md` gains a `family` headword; the report's pages use `kind` and `code` only.

The group order above is a report decision, not a second sort: it deliberately breaks global source offset order. Empty groups are omitted; rows inside a group keep the importer's offset-sorted dump order through a stable filter — no re-sort, no comparison, no locale collation. This is "within-group dump order". Mapping runs through an exhaustive `switch` on `code` with `assertNever`, so a future diagnostic code throws instead of silently vanishing, including when its group would not otherwise be rendered. The source is DDL-text import only: a live catalog read is Introspection, never Import ([ADR 0011](./0011-introspection-transport.md)), and stays with its own owner. A parse failure is an `error` row in the document; it is never presented as a clean report, and the command exits 1. A read or import failure instead prints one `schemamill: …` line on stderr with empty stdout and exit 1; skip- and flag-only findings exit 0. Object names are not re-derived: each row reuses the [ADR 0031](./0031-exclusion-diagnostic-object-names-the-table.md) rule that the object names the schema-qualified owning entity and the message carries the member detail, including the related [#188](https://github.com/osama784/schemamill/issues/188) naming contract. The [report page](../import-fidelity-report.md) is the surface contract; it references the Diagnostic DTO contract in [docs/json-output.md](../json-output.md) rather than duplicating it.

**Consequences:** A human can review one dump's fidelity findings in stable, self-describing rows, and byte-level goldens pin the document: a repeated run, or the same dump copied to another path, produces identical stdout. Every newly introduced diagnostic code must be added to the exhaustive group switch, and the fail-closed behavior is load-bearing — an unmapped code is a loud failure, not a dropped finding. The text format has no machine consumer and no version line; adding one is a separate projection with its own owner, not a field bolted onto this document. As a v1 limitation, the one-line-per-finding shape assumes object names and messages contain no tabs or newlines: a quoted identifier carrying a control character is printed verbatim and can break that shape, and no silent rewrite is attempted. Named deferrals stay with their owners: machine-readable projections (SARIF, JUnit, CI-native) with their own versioning out of [structured JSON's §Deferred](../plans/structured-json.md#deferred); introspection diagnostics parity (#71 and the folded #230); a report for export envelopes ([ADR 0023](./0023-export-projects-the-model.md)); streaming very large dumps; and fidelity scoring or a pass/fail gate. The two new [CONTEXT.md](../../CONTEXT.md) headwords are **Diagnostic** and **Report artifact**; the vocabulary law holds — fidelity is never called accuracy or completeness, a Schema is never called a model or vice versa, and a live catalog read is never called an import. No import, model, diff, plan, render, or existing ADR decision is re-litigated here.
