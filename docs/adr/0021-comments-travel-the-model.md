# 0021 — Comments travel the model

**Date/Status:** 2026-10-29 · accepted

**Context:** `pg_dump` emits `COMMENT ON` statements for the object families the model now carries — tables, columns, sequences, plain and materialized views, primary keys, unique/check/foreign-key constraints, and standalone indexes — and until this slice the importer skipped every one of them whole ([#87](https://github.com/osama784/schemamill/issues/87), the comments plan). Comments are descriptive metadata on entities whose identity is already modeled, so they raise the questions the attribute slices raised before them: where the text lives, whether it participates in equality, how a change renders when PostgreSQL drops a comment with its object, and how import attaches a comment before canonicalization strips a generated name. The accepted [ADR 0012](./0012-constraint-attributes-travel-the-model.md), [0015](./0015-column-attributes-travel-the-model.md), and [0019](./0019-views-and-materialized-views-travel-the-model.md) set the precedent that per-entity metadata travels on the entity; this ADR records the comment contract later family slices inherit.

**Decision:** `Table`, `Column`, `Sequence`, `View`, `PrimaryKey`, `UniqueConstraint`, `CheckConstraint`, `ForeignKey`, and `Index` carry an optional `comment: string`, stored verbatim — exact characters, never whitespace-normalized, unicode and newlines allowed. Absent means no comment. **The empty string is not a model value:** PostgreSQL's `CreateComments` reduces `COMMENT … IS ''` to the same removal case as `IS NULL`, and `pg_dump` never emits `IS NULL`, so `IS ''` and no comment are semantically equivalent rather than a fidelity loss; the workspace parser rejects `comment: ""` and any text carrying NUL (PostgreSQL text cannot hold it), and the renderer refuses NUL again as defense in depth.

A comment is descriptive, not structural. It is excluded from every structural equality function — indexes, unique and check constraints, foreign keys, and the primary key — and is never a `ColumnFieldChange`, `SequenceFieldChange`, or `ViewFieldChange`; it never enters `ColumnAttributes`. Including it in those equalities would decompose a comment-only change into a destructive drop and add, and PostgreSQL would drop the comment with the object.

Comment changes therefore have their own top-level change, `comment-changed`, carrying a `CommentTarget` union — one variant per `COMMENT ON` object form, with `view` carrying `materialized` and the index/constraint variants carrying the node whole so the renderer can synthesize an unnamed node's conventional name. `diff` appends the comment group last, in target identity order, and emits additions for target entities the baseline lacks; a removed entity emits nothing because its drop removes the comment, and an entity whose structural identity changed reads as absent so its comment is reported as an addition. The plan copies a change into one transactional `comment` step whose `text` is the single source of the rendered value: every copied target strips the carried node's own `comment`. Comment steps form global phase 11, after every create and identity step, so every target exists by then and comments are order-insensitive among themselves.

A recreate re-asserts a comment the drop would have taken away. Seven sites push a comment step when the target node states one: an index, primary key, foreign key, unique constraint, check constraint, or materialized/kind-change view recreate, and the synthesized dependent foreign key that `dependentForeignKeySteps` drops and re-adds when its referenced primary key changes. The terminal phase sorts the bucket by target identity and keeps one step per target, so a comment the diff already changed and a recreate re-assertion cannot render twice; both carry the target's text. A removal is never suppressed. Two structurally identical unnamed nodes with different comments share one target key and therefore one step; the model cannot distinguish the two server objects on apply, so the shape is recorded rather than forbidden.

`COMMENT ON` renders one statement per target: `TABLE`, `COLUMN`, `SEQUENCE`, `VIEW` or `MATERIALIZED VIEW`, schema-qualified `INDEX`, and `CONSTRAINT <name> ON <table>` for the four constraint kinds, with an unnamed index or constraint named by the same conventional formula its drop uses. Absent text renders `IS NULL`. Comment text renders as a plain quoted literal with embedded quotes doubled when it is line-safe, and as an `E'…'` escape string when it carries a backslash or a C0/DEL control — `\\`, `''`, `\n`, `\r`, `\t`, and `\xHH` for the other controls — so a multi-line comment stays one statement on one line and unicode passes through unchanged. NUL refuses with `RenderRefusalError`.

Import resolves each `COMMENT ON` by the stored server name while the drafts still carry it — canonicalization runs after every statement — with PostgreSQL's conventional synthesized name as the fallback for a node the source declared unnamed, so the comment stays attached after the name is stripped. The seven object forms and their arities are: table `[schema, table]`, sequence/view/matview/index `[schema, name]`, column `[schema, table, column]`, and table constraint `[schema, table, constraint]`; an unqualified form defaults to `public`, while an under-qualified column or constraint is unresolvable and flagged. `IS NULL` and `IS ''` clear the field, a repeated comment replaces the earlier one, and a repeated `CREATE` clears the comment with the rest of the entity. Text carrying NUL, an unknown or under-qualified object, a table/view kind mismatch, a view output column, and a constraint the table does not carry are all flagged, never silent; comments on unmodeled families keep the existing skip; a comment on a PostgreSQL 18 named not-null constraint takes the named deferral's own flag wording.

The workspace format gains `comment` on every entity, admitted by each entity's key list and validated by `parseNonEmptyString` plus the NUL check. Compatibility runs both ways: an older model file without the key reads unchanged as no comment, while an **older binary fails closed** on a model that carries `comment` (unknown-key rejection, [ADR 0010](./0010-workspace-container.md)) — accepted here, as it was for `views`. No format version is introduced.

**Consequences:** All nine modeled families round-trip a comment through import → diff → plan → render, including comments on unnamed nodes resolved by their conventional server names, and a recreated constraint, index, or materialized view re-asserts an unchanged comment. Comment steps are transactional and produce no hazards, so the hazard analyzer ignores the kind. Canonicalization is unchanged: a comment attaches while the server name is present and the renderer synthesizes the same name later, so no comment-aware strip branch exists. Two named deferrals remain: catalog introspection reads no comments yet (a comment-carrying model is intentionally absent from the live introspection scenes), and comments on PostgreSQL 18 named not-null constraints are flagged because the model has no not-null entity. The two follow-ups are recorded here and filed at bookkeeping.

**Deferred:** Comments on extensions ([#91](https://github.com/osama784/schemamill/issues/91)) and on unmodeled families; comments on PostgreSQL 18 named not-null constraints; catalog introspection of comments; grants, ownership, and security labels ([#92](https://github.com/osama784/schemamill/issues/92)); view output-column comments ([#143](https://github.com/osama784/schemamill/issues/143)); `COMMENT ON` deparse ([#57](https://github.com/osama784/schemamill/issues/57)); comment steps in the index-name collision guard (a residual — an unnamed comment target and a differently shaped create can share a server-form name); comment-aware canonicalization; and the owned-sequence removal rule, under which a comment follows the sequence it targets and the existing owner-removal suppression still governs whether that sequence survives.
