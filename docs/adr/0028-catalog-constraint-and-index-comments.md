# 0028 — Catalog constraint and index comments

**Date/Status:** 2026-11-14 · accepted

**Context:** The model has carried `comment` on primary keys, unique, check, and foreign-key constraints, and standalone indexes since [ADR 0021](./0021-comments-travel-the-model.md), and the dump importer has read `COMMENT ON CONSTRAINT` and `COMMENT ON INDEX` since the same slice. The live catalog read added comments only for tables, columns, sequences, views, and materialized views in [ADR 0026](./0026-catalog-comment-reads.md), and its `primaryKeys`, `constraints`, and `indexes` payload rows carried none, so a live import lost every comment on those three families and the `comment-round-trip` scene — whose target states comments on all nine modeled families — deliberately declared no `matches-import` assertion. [#146](https://github.com/osama784/schemamill/issues/146)'s promotion split the work, leaving constraint and index comments for slice 2, filed as [#192](https://github.com/osama784/schemamill/issues/192). The catalog read had to settle how each family's description is read, how absence is represented, how a primary key's repeated rows agree, how an index comment survives conventional-name canonicalization, and what to do where `USING INDEX` makes a consumed index's provenance undecidable.

**Decision:** The read gains three `obj_description` columns and no new joins. Primary-key rows read `pg_catalog.obj_description(key_constraint.oid, 'pg_constraint')`; constraint rows read `pg_catalog.obj_description(c.oid, 'pg_constraint')`; index rows read `pg_catalog.obj_description(index_relation.oid, 'pg_class')`, with `index_relation` already joined for the index definition. These are the object oids PostgreSQL stores for `COMMENT ON CONSTRAINT` and `COMMENT ON INDEX`, so no lookup or schema qualification changes.

The payload rows gain a required `comment: string | null` on `PrimaryKeyRow`, `ConstraintRow`, and `IndexRow`, added to their `expectFields` allow-lists and parsed by `expectNullableString`. Null means the object carries no comment, and the mapper omits the model key rather than attaching `''` or `undefined`, matching the five slice-1 families. The field is additive but required: a payload row missing `comment`, or carrying a non-string value, fails closed through the existing contract path. **The model needed no change:** `PrimaryKey`, `UniqueConstraint`, `CheckConstraint`, `ForeignKey`, and `Index` already carried `comment?: string`, already excluded it from their structural equality functions, and already traveled the workspace, diff, plan, and render paths under the ADR 0021 contract. This slice is a catalog read only.

A primary key is read one row per key column, so its description repeats on every row. All rows of one primary key must agree on the comment, exactly as they must agree on `deferrable`, `deferred`, and `period`; disagreement throws the existing fail-closed error, `catalog payload: primary-key rows of "<schema>.<table>" disagree on their attributes`. The mapper attaches a primary-key, unique, check, or foreign-key comment only when the row's value is non-null, and constraint canonicalization preserves the field because its conventional-name strip spreads the node's remaining fields; that preservation is now pinned directly.

Index comments have two attach points. The comment is attached at the initial `namedIndexes.push` site, because that construction would otherwise drop `indexRow.comment` before canonicalization ever runs. It is then carried through `canonicalizeIndexNames`, whose rebuilt structure type gains `comment?` and copies it in both branches: the named-keep branch (the stored name is kept) and the unnamed-strip branch (the conventional server name is dropped). `comment` stays out of every structure key — `indexStructureKey` and the constraint structure keys never read it — and out of `validateConstraintRow`'s `requirePresent`/`requireAbsent` lists; adding it to `requirePresent` would throw on every uncommented constraint. Canonicalization therefore stays comment-blind, which is the reconciliation with the `comment-aware canonicalization` deferral recorded in [ADR 0021](./0021-comments-travel-the-model.md):23's `Deferred` paragraph: resolution still happens while the server name is stored, a strip decision never consults the comment, and the comment rides alongside the structure rather than inside it. A tablespace-flagged but modeled index keeps its comment; an index or constraint row the mapper skips contributes no model row and no new diagnostic, and a commented exclusion row is still skipped whole.

**The `USING INDEX` comment divergence.** Import reads a consumed index's comment before it splices the index away and seeds the resulting primary key (`packages/postgres/src/import.ts:3746-3749`) or unique constraint (`:3693-3698`). The catalog reads only the constraint's own description, `obj_description(c.oid, 'pg_constraint')`. The backing index's description is readable — the index relation is joined and `obj_description(index_relation.oid, 'pg_class')` returns it — but `USING INDEX` provenance is not decidable from the model: the catalog shows an ordinary index-backed constraint, the same shape both inbound paths converge on, and [ADR 0016](./0016-catalog-constraint-canonicalization.md):9's `USING INDEX` provenance residual stays unresolved. The plain pg_dump flow flags a consumed comment the retained constraint cannot keep through `flagDroppedConsumedComment` (`import.ts:3642-3655`); the catalog is silent, because it never treats the backing index as consumed and has no statement at which to flag one. This ADR scopes the divergence to comments only: ADR 0016:9's structural-convergence wording is immutable and unchanged, and no structural rule moves here.

**Consequences:** A live import now returns the comments on primary keys, unique, check, and foreign-key constraints, and standalone table indexes, so a database built from a model's own plan round-trips its whole comment-carrying model through the catalog. `comment-round-trip` gains `introspection: { assert: 'matches-import' }`; the scene already carried all nine families, server-derived comment inventories, and the cross-import checks, so **no new scene** was added and the slice-1 `comment-introspection` assertion stays as it was. On a scratch PostgreSQL 16.2 the live suite is 494 tests across 53 scenes: 490 pass, and the four PostgreSQL 18 scenes skip by name. The unit suite pins each attach and omit path, both index canonicalization branches, primary-key row disagreement, the tablespace/skip behavior, and the required-field contract; the live scene is the clearing-path evidence, where a comment removed between baseline and target must come back absent.

**Invisible and deferred by name.** Comments on constraint-backed indexes have no `Index` slot — the backing index is consumed by `conindid` — and the catalog cannot recover whether the constraint's text came from the index. Comments on exclusion constraints are invisible because the constraint is skipped whole, not modeled. Comments on invalid, not-ready, or out-of-envelope indexes are invisible because the index itself is skipped and named. Matview-index comments stay unread because the index read is table-scoped and matview indexes are still proposed. Identity-sequence comments have no model slot (`Identity` carries no `comment`). View output-column comments ([#143](https://github.com/osama784/schemamill/issues/143)), view reloptions and column lists beyond the check option (ADR 0026's residual), PostgreSQL 18 named-not-null comments ([#147](https://github.com/osama784/schemamill/issues/147)), extension reads and comments ([#150](https://github.com/osama784/schemamill/issues/150)), and non-UTF-8 database encodings remain out. View outputs themselves stay unread ([#143](https://github.com/osama784/schemamill/issues/143)), and a catalog-side diagnostic for any of these classes is not introduced.

Accepted [ADR 0019](./0019-views-and-materialized-views-travel-the-model.md), [ADR 0021](./0021-comments-travel-the-model.md), and [ADR 0026](./0026-catalog-comment-reads.md) remain unedited; this ADR is the record for slice 2, and [the comments plan](../plans/comments.md) carries the slice's evidence.
