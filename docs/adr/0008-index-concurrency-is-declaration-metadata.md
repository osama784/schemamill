# 0008 — Index concurrency is declaration metadata, not structure

**Date/Status:** 2026-10-02 · accepted

**Context:** PostgreSQL refuses `CREATE INDEX CONCURRENTLY` and `DROP INDEX CONCURRENTLY` inside a transaction block, so a concurrent build cannot be wrapped with the rest of a migration and must apply bare. The constraints-and-indexes design review ([#33](https://github.com/osama784/schemamill/issues/33), round 2 decisions and the approved brief's recorded assumptions) put the declaration on the modeled `Index` and classified the two concurrent step kinds as non-transactional, extending [ADR 0007](./0007-transaction-boundaries-follow-step-semantics.md)'s per-kind classification — which was written expecting the first non-transactional kind to arrive this way. A durable decision was needed on whether the declaration is structure — part of the index's identity and equality — or apply metadata beside it, because that decides whether flipping the flag alone is a migration.

**Decision:** Import preserves the declaration: `Index.concurrently` is true exactly when the source states `CONCURRENTLY`. It is excluded from structural identity and equality, so a flag-only change produces no step at all; it only steers application. Dedicated step kinds — `create-index-concurrently` and `drop-index-concurrently`, the plan's first non-transactional steps — carry the flag through planning, and the target's flag drives a create while the baseline's drives a drop, so each half of a decomposed change follows the side it came from. The concurrent kinds are classified non-transactional in the compile-time exhaustive `TRANSACTIONAL` record and render bare in standalone groups.

**Consequences:** The model can say how to apply a build without letting an apply-time preference masquerade as a schema difference, and the planner gains its first real standalone groups instead of synthetic ones. That made the multi-group display come due: the `plan` header and section lines and the one-blank-line SQL separator between groups shipped with the same slice. `pg_dump` never emits `CONCURRENTLY`, so introspection cannot recover the declaration — an index read from a catalog imports as ordinary, and the canonicalization rule for it is named debt in the [constraints and indexes plan](../plans/constraints-indexes.md) rather than guessed here.
