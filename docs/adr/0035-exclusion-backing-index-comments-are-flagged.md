# 0035 — Exclusion backing-index comments are flagged

**Date/Status:** 2026-11-24 · accepted

**Context:** [ADR 0030](./0030-constraint-backed-index-comments-are-flagged.md) settled that a comment on the index behind a primary key or unique constraint is flagged, never copied, by both read paths; its `Deferred` paragraph left "comments on exclusion constraints, both the constraint's and its backing index's — the constraint is skipped whole" to [#90](https://github.com/osama784/schemamill/issues/90). [#231](https://github.com/osama784/schemamill/issues/231) closes only the backing-index half. A live probe established the facts both paths rely on: `pg_dump` emits `COMMENT ON INDEX public.<conname>` for a commented exclusion backing index, and for an exclusion constraint `pg_constraint.conname` equals `pg_class.relname(conindid)`, so the dumped constraint name is the index name an import can flag and the catalog can read. The documented meaning of `conindid` covers the index supporting an exclusion constraint on every server version the project tests, so nothing here moves a version floor. The exclusion constraint itself stays skipped whole with [ADR 0031](./0031-exclusion-diagnostic-object-names-the-table.md)'s object and message unchanged, and a comment on the constraint itself stays deferred on #90.

**Decision:** Both read paths flag a comment on an exclusion constraint's backing index as `dropped comment from <schema>.<index>` and neither copies it onto a model object; the model still has no `Index` slot for a constraint-backed index. On import, a table draft records each exclusion constraint's dumped `conname` when its declaration is seen — inline column-level, inline table-level, and `ALTER TABLE … ADD CONSTRAINT` — in draft-only bookkeeping that never reaches the model. A later `COMMENT ON INDEX` resolving to that schema-qualified name takes ADR 0030's exact `unsupported-attribute` flag instead of the generic flag, including for a generated, constraint-style name. An inline unnamed `EXCLUDE` has no dumped `conname` to record, so its backing-index comment keeps the generic flag; that case is deferred here beside ADR 0030's generated-name residual, and no synthesized-exclusion-name rule is added. An unknown or unrelated index keeps the generic flag, and `COMMENT ON CONSTRAINT` on an exclusion keeps its current path. On the catalog read, both backing-index `CASE` expressions select `contype IN ('u', 'x')` so an exclusion row carries `backingIndexName` and `backingIndexComment` from the existing `conindid` join; the exclusion branch of `validateConstraintRow` allows those two fields while `row.comment` stays allowed-but-unused, and the index phase emits the same dropped-comment finding, name-sorted with the primary-key and unique findings. The exclusion skip keeps ADR 0031's object and message, and a constraint's own description is read but neither modeled nor flagged.

No new surface is introduced: no model field, diff change, plan or render step, CLI switch, `CommentTarget` kind, diagnostic code, or message family. No PostgreSQL version floor moves — the live scene stays ungated at the harness floor and runs on the CI 13/18 matrix.

**Consequences:** Flag ordering is emission-code order where several flags are reachable on one index: an attribute flag first, then the `CONCURRENTLY` apply-metadata flag, then the consumed-index comment flag. The expressible two-flag order `CONCURRENTLY` → `comment` is pinned by the consumed commented concurrent primary key import test with its exact two messages; an attribute flag would precede both by code order, but no legal DDL expresses that three-flag combination — `INCLUDE` takes the whole-index skip, and `NOT VALID`, `NO INHERIT`, `NULLS NOT DISTINCT`, and `WITHOUT OVERLAPS` are either outside the documented `USING INDEX` grammar or absorbed into one flag. Pinning every expressible ordering and naming this limit is the residual's discharge; no production reordering and no misleading three-flag test is added.

The `constraint-backed-index-comments` live scene gains one exclusion case and stays one registered scene: its `flags` assertion pins the dropped-comment finding for every consumed index, and both imports agree on the flag list. Import units pin named and generated `conname` flags, the inline table- and column-level forms, an unqualified target name, coexistence with `COMMENT ON CONSTRAINT`, the unknown-index and unnamed-inline generic paths, and stable diagnostic order. Catalog units pin the exclusion backing-index flag, its name-order merge with the primary-key and unique findings, and the relaxed row contract with the constraint's own comment allowed-but-unused. No golden and no model, diff, plan, render, or CLI bytes change; a database without a commented exclusion backing index imports identically to before.

**Corrects:** [ADR 0028](./0028-catalog-constraint-and-index-comments.md):19's "a catalog-side diagnostic for any of these classes is not introduced" clause, for the exclusion backing-index class only. Its invisibility/provenance sentence — that exclusion comments are invisible because the constraint is skipped whole and the catalog cannot recover whether the constraint's text came from an index — stands unedited, as does the rest of ADR 0028; ADR 0030 already narrowed the same clause for the primary-key and unique class.

**Supersedes:** [ADR 0030](./0030-constraint-backed-index-comments-are-flagged.md):21's "Comments on exclusion constraints, both the constraint's and its backing index's — the constraint is skipped whole" deferral item, for the backing-index half only. The other half — the exclusion constraint's own comment — stays deferred on [#90](https://github.com/osama784/schemamill/issues/90). The rest of ADR 0030 stands, and neither ADR is rewritten. [The comments plan](../plans/comments.md) and [the import long-tail plan](../plans/import-long-tail.md) carry the sliced evidence.
