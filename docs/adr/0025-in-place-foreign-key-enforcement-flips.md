# 0025 — In-place foreign-key enforcement flips consult the target version

**Date/Status:** 2026-11-02 · accepted

**Context:** [ADR 0012](./0012-constraint-attributes-travel-the-model.md) made enforcement a tri-state on `ForeignKey` and `CheckConstraint` — absent meaning valid and enforced, `not-valid` for `NOT VALID`, `not-enforced` for `NOT ENFORCED` — and deferred the in-place `ALTER CONSTRAINT … ENFORCED` form by name: every attribute-only constraint change decomposed to a drop and an add, because PostgreSQL has no in-place form for checks and drop/add is deterministic. PostgreSQL 18 added `ALTER TABLE … ALTER CONSTRAINT … ENFORCED | NOT ENFORCED` for foreign keys, so a pure enforcement change has a second, smaller statement form. [ADR 0024](./0024-synthesized-forms-consult-the-target-version.md) then put the declared PostgreSQL major into `renderSql(plan, options?)` and closed its synthesized-form consumer list at the two reset forms that refuse below their floor, while keeping `plan()` version-free ([target-version plan](../plans/target-version.md) D6). [#133](https://github.com/osama784/schemamill/issues/133) is the reason that plan-time parameter was kept out: the form choice can be made at render time from the plan the diff already produces.

The model's tri-state is `absent` = (`conenforced`, `convalidated`) = (true, true), `not-valid` = (true, false), and `not-enforced` = (false, false). PostgreSQL 18's `ALTER CONSTRAINT` sets `conenforced = is_enforced` and, when that changes the enforced state, sets `convalidated` to match — the tightening form validating existing rows, the relaxing form forcing `convalidated = false` — while an already-matching enforced state is a no-op. That action makes only part of the transition space expressible in place:

| before | after | in place | form |
|---|---|---|---|
| absent | not-valid | no — the ALTER cannot unvalidate | drop/add |
| not-valid | absent | no — `ENFORCED` on an already-enforced constraint is a silent no-op that does not validate | drop/add |
| absent | not-enforced | yes | `NOT ENFORCED` |
| not-valid | not-enforced | yes | `NOT ENFORCED` |
| not-enforced | absent | yes — `ENFORCED` validates (data-dependent) | `ENFORCED` |
| not-enforced | not-valid | no — `ENFORCED` overshoots to absent | drop/add |

**Decision:** `renderSql` recognizes a `drop-foreign-key` paired with a matching `add-foreign-key` as one pure enforcement change and, at a target of PostgreSQL 18 or newer, emits one `ALTER TABLE <table> ALTER CONSTRAINT <name> <form>;` at the drop step's position and suppresses the add statement entirely — no placeholder, no empty line. The plan keeps its semantic drop+add decomposition and remains version-free; the pairing pass reads the plan and never rewrites it, so one plan still renders for several targets.

**The three legal transitions, two forms.** Only the rows marked "yes" collapse: any transition into `not-enforced` relaxes with `NOT ENFORCED` (from absent or `not-valid`), and `not-enforced` back to the absent default tightens with `ENFORCED`. Validation-only transitions (`absent ↔ not-valid`) and `not-enforced → not-valid` stay drop/add.

**PostgreSQL 18 semantics.** `NOT ENFORCED` sets `conenforced = false` and forces `convalidated = false`; it does not scan, and the foreign key's RI triggers stop checking subsequent rows. `ENFORCED` sets both flags true and validates the referencing table as part of the statement, so it can fail on existing rows exactly as `ADD FOREIGN KEY` can; on an already-enforced constraint it is a silent no-op, which is why it cannot turn `not-valid` into absent. Both directions take `ALTER TABLE`'s default ACCESS EXCLUSIVE lock. PostgreSQL 18.0–18.3 lose a `DEFERRABLE` foreign key's `tgdeferrable`/`tginitdeferred` trigger attributes when the constraint is toggled `NOT ENFORCED → ENFORCED`; the fix landed in 18.4.

**Eligibility (the collapse happens at target ≥ 18 only when every rule holds).** (a) One `drop-foreign-key` and one `add-foreign-key` on the same table, with every field but `enforcement` equal by strict raw comparison — `name`, `columns`, `referencedTable` schema and name, raw `referencedColumns`, `onUpdate`, `onDelete`, `deferrable`, `initiallyDeferred` — and `comment` ignored, because a comment change is its own step and survives either form; (b) the transition is one of the three legal rows above; (c) no other non-`comment` step in the plan has the referencing table or the referenced table as its **principal** table identity — the table the step alters, not a table mentioned inside a payload such as another foreign key's `referencedTable`, a sequence's `ownedBy`, or a view body — and the pair's own two steps are excluded from that count; (d) both halves lie in the same `plan.groups` group, so a concurrent index between them (which necessarily splits the group) keeps drop/add; (e) a tightening direction (`not-enforced → absent`) is not deferrable, because a major-only target cannot distinguish 18.0–18.3 from 18.4 (D6 above); (f) exactly one add matches the drop and exactly one drop matches the add — a drop matching two adds or an add matching two drops throws a plain `Error` before emission, like `assertGroupsTileSteps`, while a lone half is normal and renders unchanged. The pair's ALTER may move to the drop position because rule (c) guarantees no other work on either table, so nothing can observe the FK between the old drop and add slots.

**Target gate.** At a declared target of 18 or newer the eligible pair collapses; below 18 the renderer emits exactly today's drop+add pair, byte-identically, not a refusal. The plan is valid at every target and the fallback is the same migration semantically. This is the split ADR 0024 introduced: declarations render as declared, a synthesized reset refuses below its floor, and a form with an equivalent fallback selects the fallback.

**Naming and hazards.** The ALTER names its constraint `after.name` when explicit (quoted as stored) and `synthesizedForeignKeyName(table, after)` when unnamed — the same rule the existing drop path uses, collision-suffix names staying an offline residual. No hazard class is added: the analyzer has no foreign-key hazard today, and [the hazards plan](../plans/hazards.md#deferred-gaps) (`:49`) already records that `add-foreign-key` validates existing rows flaglessly. The in-place path has the same data-dependent validation and no new flag; version-aware hazards remain [#163](https://github.com/osama784/schemamill/issues/163). Import is untouched: there is no `AT_AlterConstraint` branch, an occurrence falls through the generic alter-table skip and is named there, and `pg_dump` 18 emits `NOT ENFORCED` inline on `ADD CONSTRAINT`, so dump round-trip is unaffected.

**Consequences:** At target 18 a pure enforcement change now renders one `ALTER CONSTRAINT` statement instead of a drop and an add — smaller and lock-comparable, but still data-dependent in the tightening direction, where `ENFORCED` scans and can fail on existing rows. The default target 13 path is byte-identical, so every existing golden and the CLI's default output stay unchanged; a new target-18 postgres golden, the `constraint-enforcement` CLI scene, and the `enforcement-in-place` live scene pin the two forms, and the live scene skips below PostgreSQL 18 by name. The plan display still shows the semantic drop+add pair while the SQL shows the ALTER — intentional, because the plan is version-free and the target is a render option. The renderer restates the diff's foreign-key field list; the strict equality is conservative — a pair it does not recognize keeps the always-correct drop/add.

Named residuals, none silent: validation-only transitions (`absent ↔ not-valid`) and `not-enforced → not-valid`; CHECK enforcement flips, which PostgreSQL 18 rejects on non-foreign-key constraints and PostgreSQL 19 extends to checks; two pure flips on the same table, which see each other as crowd and keep drop/add; an empty-vs-explicit `referencedColumns` pair, which keeps drop/add because the predicate is stricter than the diff's primary-key equivalence; collision-suffix names; partitioned and temporal foreign-key shapes, which the model cannot carry (partitioned relations are skipped, `PERIOD` is flagged and dropped); pairs split across transaction groups; and CLI/studio disclosure of the in-place choice.

**Amendment by correction, not supersession.** ADR 0024 recorded the convention: "Accepted ADRs are immutable, so ADR 0014 stands as written and this paragraph is the correction" (ADR 0016), and its own paragraph narrowed ADR 0012/ADR 0015's "negotiates no server version" to **declarations**. In the same way, ADR 0024's closed list of "exactly two synthesized forms" and its sentence that "only the renderer's own synthesized forms consult the target" describe the reset-only state before this slice; they are corrected here to two classes of target consumer — a synthesized form that refuses below its floor, and a form choice with an equivalent fallback that selects the fallback below its floor. ADR 0012's deferral of the in-place form is now taken up for the three legal transitions; ADR 0012 and ADR 0024 remain accepted and unedited, and this ADR is the record for the form choice.
