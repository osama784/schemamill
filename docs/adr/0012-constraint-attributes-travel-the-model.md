# 0012 — Constraint attributes travel the model

**Date/Status:** 2026-10-10 · accepted

**Context:** Constraint attributes outside the model were flag-and-drop: a `NOT VALID` or `NOT ENFORCED` check constraint or foreign key was flagged, deferrability was flagged and dropped, and PostgreSQL 18's named `NOT NULL` constraints had nowhere to live — the inline name kept the column's nullability while the name itself was lost, and the table-level and post-data forms were skipped. The two enforcement wordings arrive through the parser's one `skip_validation` channel (`NOT VALID` carries `is_enforced: true` beside it, `NOT ENFORCED` omits it), and PostgreSQL's catalog cannot distinguish a combined `NOT VALID NOT ENFORCED` declaration from `NOT ENFORCED` alone, so the wordings had to be told apart at import. The slice ([#74](https://github.com/osama784/schemamill/issues/74), [plan](../plans/constraint-attributes.md)) needed model shapes for enforcement, deferrability, and the not-null name before import, diff, plan, and render could carry a declaration through the whole path.

**Decision:** A check constraint or foreign key carries a single enforcement tri-state — `enforcement?: 'not-valid' | 'not-enforced'`, absent meaning valid and enforced — because the combined declaration is not round-trippable as a distinct value: PostgreSQL reports it as `NOT ENFORCED`, so the model never conflates the two wordings and import decodes the channel by the `is_enforced` discriminator, with render stating `NOT VALID` or `NOT ENFORCED` as declared. A primary key, unique constraint, or foreign key carries `deferrable?: boolean` and `initiallyDeferred?: boolean`, with import normalizing `INITIALLY DEFERRED` to imply `DEFERRABLE`. A not-null constraint's name lives on the column — `Column.notNullName`, meaningful only with `notNull: true` — because one not-null fact per column is the model's shape and there is no separate not-null constraint object to name. An attribute-only constraint change stays the existing changed-constraint kind and decomposes to its drop and add halves — PostgreSQL has no in-place `ALTER CONSTRAINT` for checks, and drop-and-add is deterministic and mirrors the existing changed-constraint doctrine — while a not-null fact or name change decomposes to the new `drop-not-null`/`add-not-null` steps, with no synthesized names. Explicit defaults — `NOT DEFERRABLE`, `INITIALLY IMMEDIATE`, `ENFORCED` — are consumed as faithful no-ops on the kinds that accept them, because they restate the model's absent-means-default shape rather than adding information. PostgreSQL 18-only syntax is rendered as declared: the renderer negotiates no server version, because the source carried the declaration.

**Consequences:** A dump of a `NOT ENFORCED`, `DEFERRABLE INITIALLY DEFERRED`, or named `NOT NULL` constraint round-trips to an empty diff, with the generated not-null name canonicalized to unnamed; the canonicalization strip needs no twin guard, because one not-null fact per column is the only shape the model carries and a duplicate declaration is already collapsed by the import merge. Deferred, by name: not-null `NOT VALID` modeling; multiple named not-null constraints per column; truncation and collision-suffix boundaries (the [render-refusal plan](../plans/render-refusal.md)); introspection parity (the [introspection-attributes plan](../plans/introspection-attributes.md), [#60](https://github.com/osama784/schemamill/issues/60) and [#77](https://github.com/osama784/schemamill/issues/77)); `NO INHERIT` not-null constraints; the in-place `ALTER CONSTRAINT … ENFORCED` form; constraint-validation hazards (the [hazards plan](../plans/hazards.md)); and exclusion constraints.
