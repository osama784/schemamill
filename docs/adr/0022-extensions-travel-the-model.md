# 0022 — Extensions travel the model

**Date/Status:** 2026-10-29 · accepted

**Context:** `pg_dump` installs extensions before the objects that use them and emits a `COMMENT ON EXTENSION` for each commented one, while the importer skipped both statements whole and the model had no extension shape ([#91](https://github.com/osama784/schemamill/issues/91), Slice E of the [import long-tail plan](../plans/import-long-tail.md)). Extensions are the first model family whose identity is not schema-qualified: PostgreSQL extension names are database-unique, and the install schema is a property of the installed extension, not part of its name. That raises questions the earlier family slices did not: whether the install schema is required, how a schema move differs from a drop and create, where the create and teardown belong among the global phases, and what a removal means when other objects depend on the extension. The accepted [ADR 0002](./0002-canonical-model.md), [0009](./0009-render-refuses-duplicate-conventional-names.md), [0010](./0010-workspace-container.md), [0019](./0019-views-and-materialized-views-travel-the-model.md), and [0021](./0021-comments-travel-the-model.md) stand as written; this ADR records the extension contract.

**Decision:** `Model` gains a required `extensions` array, and `Extension` is `{ name; schema; comment? }` with `ExtensionIdentity` reduced to `{ name }`. **The name alone is identity** — database-unique and never schema-qualified — and the array is sorted by name alone, so a schema move is an `extension-changed` with a value-carrying `{ field: 'schema'; before; after }`, never a removal plus an addition. **The install schema is required.** `pg_dump` always states `WITH SCHEMA`, so every imported extension has one; a hand-authored `CREATE EXTENSION` without one is skipped and named `skipped CREATE EXTENSION <name> (no WITH SCHEMA)`, because the importer must not invent an install schema, and a skipped definition never replaces an already imported draft. The comment follows the [ADR 0021](./0021-comments-travel-the-model.md) contract exactly: absent means none, the empty string and NUL are rejected, and the text is never normalized.

Import reads the dump's two forms. `CreateExtensionStmt` takes the extension name and the `schema` option; `IF NOT EXISTS` is restore noise and is ignored with no diagnostic. **`VERSION` and `CASCADE` are flagged, not modeled:** a dump never emits them, so they exist for hand-authored DDL only, and the extension still imports after `dropped VERSION from extension <name>` or `dropped CASCADE from extension <name>`. An unknown option takes `dropped <defname> from extension <name>`; the message uses the established `dropped <description> from extension <name>` shape with the bare name, not `flagAttribute`, whose `from <identity>` tail assumes a schema-qualified object. `COMMENT ON EXTENSION` joins the modeled comment objects and resolves its `String` object by the same bare name; a comment before its create is flagged, never turned into a phantom extension. **Members and teardown are excluded by name:** `ALTER EXTENSION … UPDATE`, `SET SCHEMA`, and `ADD`/`DROP`, plus `DROP EXTENSION`, stay skipped with accurate wording, and built-in extensions such as `plpgsql` are never dumped, so they are never modeled. Normal dumps exclude extension members and never emit `ALTER EXTENSION … ADD`; that form is binary-upgrade-only.

The plan treats the extension lifecycle as two ends of the thirteen-phase order. **Creates are global phase 1**, before every other object, because any table, view, or expression may use an extension's type or function. **Comments are phase 12**, the terminal comment phase, and the extension comment target is name-only, so the later schema move cannot disturb it; a removed extension emits no comment step because its drop takes the comment with it. **Alters and drops are phase 13, last**: `alter-extension` runs in name order, then `drop-extension` in name order, after every dependent object and every comment. `alter-extension` carries identity plus value-carrying fields, so the renderer reads the destination from `schema.after` and needs no baseline lookup. All three kinds are transactional.

Render is deliberately total and deliberately plain: `CREATE EXTENSION <name> WITH SCHEMA <schema>;`, `ALTER EXTENSION <name> SET SCHEMA <schema>;`, `DROP EXTENSION <name>;`, and `COMMENT ON EXTENSION <name> IS <literal|null>`. **There is no `IF NOT EXISTS`** — its only purpose is to tolerate drift, and drift must surface at apply; pg_dump's clause is restore noise. **There is no relocatability preflight:** `ALTER EXTENSION … SET SCHEMA` is legal only for a relocatable extension, the model carries no `relocatable` bit, and the server enforces the rule, so a non-relocatable move fails loudly at apply rather than being guessed offline. **There is no new refusal class:** none of the three statements is structurally impossible.

**Extension removal with dependents is a named RESTRICT class**, recorded beside the view-dependency doctrine in the plan's phase 5 note (`plan.ts:126–131`): `DROP EXTENSION` defaults to `RESTRICT`, so a kept object that depends on a removed extension fails at apply, exactly as a kept view whose definition references a dropped object does. The plan does not cascade, does not preflight `pg_depend`, and does not suppress the drop; a dependent-aware extension graph is a follow-up, not a silent behaviour.

**The catalog is deferred.** `catalog.ts` keeps returning `extensions: []`, mirroring its `views: []`. A model carrying extensions is intentionally not what the catalog read returns, so a live-database import loses extensions with no diagnostic until the follow-up lands; every `matches-import` scene stays extension-free, and the `extension-round-trip` scene declares no introspection check. The two named follow-ups are a `pg_extension` read (with `obj_description` comments) and catalog member filtering, the [ADR 0018](./0018-catalog-sequences-and-identity-columns.md) residual. The asymmetry is accepted and recorded rather than hidden.

**Workspace compatibility runs both ways.** `extensions` joins `MODEL_KEYS`; an older model file without the key reads as `[]`, while `null`, a non-array, an unknown key, a malformed object, an empty name or schema, or an empty/NUL comment fails closed. Serializers write `{ schema, name, ...(comment) }` after `views`; an **older binary fails closed** on a model that carries `extensions` (unknown-key rejection, [ADR 0010](./0010-workspace-container.md)), accepted as it was for `views`, and no format version is introduced.

Two defensive branches are pinned through test seams rather than through DDL. **`ALTER EXTENSION … RENAME` is invalid PostgreSQL** — there is no such statement — so the `RenameStmt` describe branch is unreachable through `importDump` and is pinned by calling `describeStatement` directly. **The unknown-extension-option flag is grammar-unreachable**: the extension grammar admits only `SCHEMA`, `VERSION`, and `CASCADE`, so the catch-all is pinned by calling the exported `readCreateExtensionOptions` with a fabricated `DefElem`. Both branches keep the skip and flag paths total without pretending the forms are reachable.

**Consequences:** Extensions now round-trip through import, diff, plan, and render with their install schema and comment, and a relocatable schema move is an `ALTER EXTENSION … SET SCHEMA` rather than a destructive recreate. Three step kinds join the union (33 kinds, 31 transactional), the thirteen global phases renumber every extension-adjacent reference, and the CLI and goldens show extension changes and steps. The gated `extension-round-trip` scene proves the round trip with server-derived catalog checks and a deep-equal cross-import. The named costs are: a schema-less create is skipped rather than defaulted, a non-relocatable move and a removal with dependents fail at apply, `VERSION`/`CASCADE` are discarded with flags, and catalog parity remains absent. The deferrals below stay visible in the [plan](../plans/extensions.md).

**Deferred:** Version modeling and `--exclude-extension` gating ([#57](https://github.com/osama784/schemamill/issues/57)); extension ownership; member-object modeling and `ALTER EXTENSION … ADD`/`DROP`; binary-upgrade dumps; catalog `pg_extension` reads and comment introspection (follow-up filed at bookkeeping); catalog member filtering (the ADR 0018 residual); built-in extensions; `extconfig` data semantics beyond the dump's own tables; `DROP EXTENSION` with `--clean` dumps; and extension-availability checks.
