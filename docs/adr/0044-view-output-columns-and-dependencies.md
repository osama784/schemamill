# 0044 — View output columns and dependencies travel the model

**Date/Status:** 2026-11-28 · accepted

**Context:** [ADR 0019](./0019-views-and-materialized-views-travel-the-model.md) shipped views and materialized views as relations carrying an opaque definition, and named two follow-ups: output-column modeling to preflight `CREATE OR REPLACE`, and a dependency graph with topological drop/create ordering ([#143](https://github.com/osama784/schemamill/issues/143)). PostgreSQL enforces both facts at apply time and offers no room for a repair: `CREATE OR REPLACE VIEW` accepts only unchanged names, order, and types for the existing prefix (appending at the end is allowed), and `DROP … VIEW RESTRICT` fails while another view holds a `_RETURN` dependency through `pg_rewrite`/`pg_depend`. The planner saw neither fact: every plain-view change emitted one `replace-view`, and view steps were sorted by identity only. A plan could therefore be individually sound yet unsatisfiable when a column changed incompatibly, when a base was dropped before its dependents, or when a dependent was created before its base. The catalog read took `pg_get_viewdef`, `check_option`, and the comment but no columns or dependency facts, while the dump importer flagged a parenthesized view column list and discarded its names. `planOrReport` caught only `SequenceOwnershipError` ([ADR 0027](./0027-plan-refuses-dangling-target-ownership.md)), so any new plan-time guard needed a channel as well as a rule. A decision was needed on which facts the model carries, what counts as evidence to rewrite, which graph side governs which phase, and where a refusal lives.

**Decision:** `View` gains two optional fields. `columns` is an ordered list of `{ name, type }` in `attnum` order, where `type` is canonical `format_type` text and `''` means "type unknown"; absence means no facts were recorded. `dependsOn` is a list of `{ kind: 'view' | 'relation', schema, name }`; the required discriminator is what keeps a table or sequence fact from ever being read as an unmodeled view. Both keys are accepted by the workspace reader and written only when present. The CLI's human `compare` diagnostic prints changed output columns and their incompatibility, and the JSON DTOs carry both fields in change and step model payloads; Markdown export projects neither field. An older reader rejects them as unknown keys, so this is an intentional compatibility consequence rather than a silent migration (see Rollback below).

The catalog read extends the `views` payload with columns from `pg_attribute`/`format_type` in `attnum` order and with dependencies from the full `pg_rewrite` → `pg_class` → `pg_depend` → `pg_class` join: `r.ev_class` supplies the owning view, `d.refobjid` the referenced relation, and `deptype IN ('n', 'a')` with `refobjsubid = 0` selects view-to-relation facts. Relkind mapping is total: `v`/`m` become `view`, and `r`/`p`/`f`/`t`/`S` plus every other kind become `relation`, so a view depending on a sequence is recorded rather than dropped. The dump importer records target-list `ResTarget.name` names in order and resolves each unqualified relation name against the view's own schema; a parenthesized `ViewStmt.aliases` list is still flagged and discarded, and a partially aliased column list is treated as unknown as a whole. The importer writes `type: ''` because a dump's types cannot be resolved offline without `search_path`-sensitive name resolution.

**Compatibility is positive-evidence only.** A side is *verifiable* iff its `columns` is present, non-empty, and every entry carries both a name and a canonical non-empty type — trimmed, whitespace-collapsed, lowercased. Catalog lists are verifiable; importer lists are not. If either side is absent or unverifiable, `viewColumnIncompatibility` returns `compatible`: the plan keeps `replace-view`, with the named residual that a rename or retype visible only on a dump-derived side cannot be preflighted, and PostgreSQL still validates the replace atomically at apply. Destructive rewrite requires two verifiable sides. Then names and canonical types must match for the existing prefix; appending trailing columns is compatible. A dropped, renamed, reordered, or retyped existing column yields the single comparison rule, and `plan` emits the already-existing `drop-view` plus view-index drops, `create-view` plus view-index creates branch instead of `replace-view`. `diff` carries `{ before, after, column, reason }` on `ViewFieldChange.columns`, the human formatter prints `columns <old-list> → <new-list> (incompatible: <column> <reason>)`, and the JSON projection carries the same fields; the fallback without the parenthetical stays for lists with no named offender. No step kind and no hazard kind is added, so the transaction classification and the step-count pins are unchanged.

**Ordering uses two graphs, deliberately.** View drops are topologically ordered dependents-first on the **baseline** dependency graph before the table phases, because the live database holds the baseline's `_RETURN` rows at drop time; view creates and replaces are ordered dependencies-first on the **target** graph after the table phases, because the target is the structure being built. Ties are stable by schema and name, and a materialized view's index steps stay adjacent to its view step. The blocking graph is also the baseline's: before a view is recreated, every transitive baseline dependent must either be scheduled as a drop ahead of the base or be converted from `viewReplaces` into drop+create. A dependent merely scheduled as a `replace-view` would keep its `_RETURN` row while the base is dropped, since `CREATE OR REPLACE` never drops the old relation, so it is converted; an unchanged dependent cannot be converted without inventing a diff-less change and therefore blocks. Cycle and unmodeled-view checks are scoped to views actually scheduled for drop or create, not to a global scan, so a table-only plan against a cyclic database is unaffected. A `kind: 'relation'` fact — a table or a sequence, modeled or not — is recorded for fidelity but never orders a view and never refuses; ADR 0019's well-formedness case (e) stays a residual.

**Unmodeled dependency, closed.** An unmodeled dependency means specifically a `kind: 'view'` fact that names a schema-qualified view absent from the dependency side's `Model.views`, on a scheduled view. It is never a table or sequence fact, and never an unscheduled view's fact. This closes the loose wording in ADR 0019's deferral without changing that file.

**The refusal is typed and plan-time.** `plan` throws the exported `ViewDependencyError`, carrying `reason`, independent copies of the named `views`, and (for the unmodeled case) the `dependencies`. All three messages name every member in identity order:

- `blocking-dependent`: `view dependency: view public.base cannot be recreated while dependent views public.dep are not scheduled for drop`
- `cycle`: `view dependency cycle among views public.a, public.b`
- `unmodeled-view`: `view dependency: view public.a depends on unmodeled view public.missing`

`planOrReport` catches `ViewDependencyError` alongside `SequenceOwnershipError`; every other error still propagates as a bug. `plan`, `compare`, and `export` — DDL and JSON alike — therefore write one `schemamill: <message>` line to stderr with exit 1 and no artifact, and the two contract comments in `cli/run.ts` describe both errors. [ADR 0027](./0027-plan-refuses-dangling-target-ownership.md) remains accepted and unedited: its objection was to a hazard annotation that leaves the failing step emitted, so a caller ignoring hazards still fails at apply. A typed preflight that builds no step is the other side of that boundary, and this ADR records it as the second error the CLI catches.

**Live evidence and its boundary.** The gated suite gains a successful dependent-view chain scene and a standalone-column scene proving a rename and a retype. Refusals have no live claim: a `plan()` throw aborts the harness before a scene's own checks run, so the cycle, unmodeled-view, and blocking-dependent cases are pinned by unit and CLI tests only. Because the catalog read now reports columns and dependencies while dump imports carry `type: ''` and no dependency list, `matches-import` parity for those two fields is explicitly out of scope under #71. The harness stays generic: a scene-level `introspectionIgnore: readonly ('view.columns' | 'view.dependsOn')[]` normalizes those fields out of both sides before `assertIntrospection`'s `matches-import` deep-equality, and every view-bearing scene declares it. No local `SCHEMAMILL_TEST_PG_URL` was configured, so live pass/skip counts come from CI only; the corpus is 564 postgres tests + 63 scenes + 4 always-on live subtests = 631 tests, and the five PostgreSQL 18 scenes remain floored.

**Rollback is forward-incompatible.** A workspace written by this slice can carry `columns` and `dependsOn`. Because no format version is introduced ([#54](https://github.com/osama784/schemamill/issues/54)), reverting to a pre-slice binary makes those files fail to parse as unknown keys until they are re-saved without the two keys. That is deliberate: the alternative — silently dropping facts on read — would turn an unreadable file into a wrong migration. Forward compatibility (a new reader accepting an old file) is preserved.

**Consequences:** A changed view no longer reaches apply with a column incompatibility the planner could see, and the common dependency-order failures are either ordered or refused before a step is emitted. Valid short plans, non-view plans, and plans with absent or dump-derived columns are byte-identical to before. The model gains facts it cannot fully verify offline, so the verifiability predicate, not mere presence, gates every rewrite.

Named residuals: PostgreSQL 15 added a collation check to `CREATE OR REPLACE VIEW` that the model does not carry; `format_type` spelling of a custom type can diverge with `search_path`, so canonical comparison is textual only; unqualified dump relation names resolve with the view's own schema rather than the dump-time `search_path`; table and sequence dependencies are recorded but never refuse, including the kept-view-references-dropped-relation case; a rename or retype visible only from a dump-derived side stays unpreflighted; and catalog-versus-import parity for the two new fields is not claimed under [#71](https://github.com/osama784/schemamill/issues/71). Output-column comments stay deferred under this issue; a matview rewrite's data/index/grant loss stays deferred, as does `ALTER VIEW`, `#56` rename detection, and workspace versioning.

**Amendment by correction, not supersession.** [ADR 0019](./0019-views-and-materialized-views-travel-the-model.md) remains accepted and unedited. Its `:5` context sentence — that a view "has no modeled columns, types, or structure from which a query could be reconstructed" — is narrowed here: a view now carries ordered output columns and typed dependency facts, but its definition remains opaque and no query is reconstructed, so the original exception to generated-SQL doctrine stands for the definition alone. Its `:21` deferred list is narrowed here: view output columns and a view dependency graph with topological ordering are built by this decision, while dependency-aware hazards are deliberately not (per ADR 0027's reasoning above); output-column comments, catalog parity, `ALTER VIEW`, `CREATE TABLE AS`, matview residuals, and workspace versioning stay deferred. [ADR 0027](./0027-plan-refuses-dangling-target-ownership.md) is untouched; its second caught plan-time error is recorded here rather than edited into it.
