# 0009 — Render refuses duplicate conventional names

**Date/Status:** 2026-10-06 · accepted

**Context:** An unnamed member takes PostgreSQL's conventional name when it applies — `<table>_<cols>_idx` for an index, and `<table>_pkey`, `<table>_<cols>_key`, `<table>_<cols>_fkey`, and the check forms for constraints — and a name is optional metadata in the model, not structure, so an unnamed index and an explicit twin can coexist while both resolve to one name. The naming-boundaries slice ([#48](https://github.com/osama784/schemamill/issues/48)) reproduced the failure: with an unnamed index and an explicit `t_a_idx` on one table, `renderSql` emitted two same-name statements and PostgreSQL rejected the second at apply, and a baseline holding both rendered the same `DROP INDEX` twice. Rendering could rename, suppress, or reorder one of the statements, but each trades an unsatisfiable plan for SQL that fails at apply or quietly drops the model's intent; a decision was needed on what rendering does with a plan it cannot express.

**Decision:** `renderSql` validates the plan before rendering it and throws the new exported `RenderRefusalError` when two index statements of one table and polarity resolve to one name — the explicit name for a named index, PostgreSQL's conventional name for an unnamed one — because two creates would collide at apply and two drops would drop one name twice; explicit-vs-explicit duplicates are refused too. A drop and a create of one name are different statements (`index-changed` decomposes that way) and render. The guard is a sibling of the partition assertion and runs before any SQL is produced, and it considers same-table groups only: an index name's uniqueness spans its schema, which the plan does not model. `@schemamill/cli`'s `plan` catches exactly this class, keeps the plan display on stdout, writes `schemamill: refusing to render: …` to stderr, and exits 1, while any other render failure still crashes.

**Consequences:** The model's intent survives rendering: nothing is renamed, suppressed, or reordered to make an unsatisfiable plan render, and a pathological model is refused loudly for the user to resolve rather than failing half-way through apply. The boundary is index-only and plan-local: constraint twins (same-kind or cross-kind), explicit-vs-explicit constraint-name collisions, cross-table same-schema index-name collisions, unnamed predictions that only collapse under PostgreSQL's 63-byte truncation, and a baseline-materialized unnamed index a target's explicit twin create would collide with all stay deferred, as does surfacing the refusal through the hazard channel. The deferred list is carried by the [constraints and indexes plan](../plans/constraints-indexes.md).
