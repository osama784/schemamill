# 0027 — Plan refuses dangling target ownership

**Date/Status:** 2026-11-14 · accepted

**Context:** A sequence carries optional ownership as `ownedBy` — the table and column it serves ([ADR 0018](./0018-catalog-sequences-and-identity-columns.md)) — and the plan's ownership attach renders as `ALTER SEQUENCE … OWNED BY`. `plan()` builds that attach from the diff's `ownedBy` field change without resolving the owner against the target model: its contract paragraph stated the assumption that a sequence's `ownedBy` names a table and column the model contains, and that the plan validates nothing. A hand-edited workspace `model.json` can therefore declare `ownedBy` naming a table or column the target does not carry, and `plan()` returns a plan whose attach cannot execute; apply fails at the `OWNED BY` statement with PostgreSQL's missing-relation or missing-column error. Import-side validation ([#136](https://github.com/osama784/schemamill/issues/136)) skips such a sequence whole and names the skip, and the catalog read has the same disposition, but both only cover models those paths produced. The hand-edited and workspace path is outside import, and a workspace's `model.json` is validated for shape only — the writer deliberately does not read the model ([ADR 0020](./0020-model-persistence-writes-atomically.md)) — so [#189](https://github.com/osama784/schemamill/issues/189) needed a decision on where the refusal lives and how much it validates.

**Decision:** `plan()` resolves every target sequence's `ownedBy` against the target model before it builds any step, before `diff()` runs, and throws the new exported `SequenceOwnershipError` when the owner table or its column is absent. The guard walks a copy of the target sequences in identity order — schema, then name — so the reported offender is the smallest dangling identity whatever order the model's array arrives in; the owner table is looked up by schema and name before the member column, so an owner whose table and column are both missing reports `missing: 'table'`. Unowned sequences and target sequences without `ownedBy` are unaffected, and a zero-diff pair whose target still carries a dangling owner throws: the guard is not coupled to diff content.

The error extends `Error` — core's first exported `Error` class, with `RenderRefusalError` in `@schemamill/postgres` as the shape precedent — sets `name = 'SequenceOwnershipError'`, and carries independent copies, never live model references, of `sequence: SequenceIdentity`, `owner: SequenceOwner`, and `missing: 'table' | 'column'`. The message is one line and spells identities as the model does, unquoted:

- missing table: `sequence public.s is owned by public.absent.id, but the target model has no table public.absent`
- missing column: `sequence public.s is owned by public.t.id, but the target model has no column id on table public.t`

`plan()` validates nothing else: foreign-key targets, key columns, and a table's unique column names stay assumptions, as the corrected contract paragraph says. `applyChange` stays non-validating — it is the change-application seam, not a plan entry point, and its fabricated-owner fixtures continue to exercise it without a model pair. Import and introspection remain where well-formedness comes from for the paths they own.

**Target-only, deliberately.** The goal is the emitted ownership attach, so only the target — the desired state — is validated. The renderer emits an ownership statement only from an `after` value, or as `OWNED BY NONE` for a detach; a baseline owner becomes a `before` value or feeds the detach and drop-suppression rules, never an attach. A baseline-only hand-edit therefore still plans by design, including through the CLI's one-path workspace-as-baseline default, which places the resolved workspace on the baseline side of a dump comparison. This is the deliberate reading of the acceptance, not an oversight: validating the baseline would refuse plans whose target is well formed and whose repair path is otherwise available, and a baseline owner that is dangling has no attach to emit.

**Alternatives.** Two alternatives were rejected. A hazard-channel annotation would leave the plan renderable: it would still emit the attach that cannot execute and report a warning, so a caller that does not read hazards still fails at apply — and hazard analysis is dialect-specific and lives in `@schemamill/postgres`, while resolving an owner against the model needs nothing dialect-specific and belongs in core beside `plan()` ([ADR 0005](./0005-framework-free-core.md)). Repair-with-diagnostic would need a diagnostic channel in `plan()`, which the seam does not have — the only result is a `Plan` — so the guard would have to drop or rewrite the attach and guess the user's intent. Failing loud, before any step is built, was chosen.

**Consequences:** A malformed target that previously produced a broken plan now throws a typed error naming the sequence, the owner, and which lookup failed; valid targets, valid zero-diff pairs, and every existing fixture behave as before. The acceptance is defined at `plan()`, so the CLI is out of scope: this is likely the first catchless core throw reachable from `compare`, `plan`, or `export`, and until a plan-error channel lands a corrupt workspace model surfaces as a stack trace. That channel — one `schemamill: …` line on stderr and exit 1, matching the render-refusal contract — is a named follow-up.

**Named residual.** The guard validates target owners only. A removed sequence whose owner table exists in the baseline but whose owner **column** the baseline lacks — where the target removes that table — still suppresses the explicit `drop-sequence` through `removedTableKeys`; PostgreSQL's cascade does not remove the sequence because the owner column never existed, so the sequence is left behind. That is a database leak, recorded here and pinned by the plan test `a baseline owner column the baseline lacks still suppresses the explicit drop` (T10 in the slice brief), not validated; a repair path stays allowed. Baseline-side `ownedBy` validation, the CLI's one-path workspace-as-baseline default, workspace-boundary cross-reference validation ([#159](https://github.com/osama784/schemamill/issues/159)), and the remaining `plan()` assumptions are the other named deferrals.

Accepted [ADR 0018](./0018-catalog-sequences-and-identity-columns.md) and [ADR 0020](./0020-model-persistence-writes-atomically.md) remain unedited; this ADR is the record for the plan-time ownership guard.
