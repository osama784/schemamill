# 0007 — Transaction boundaries follow step semantics

**Date/Status:** 2026-10-02 · accepted

**Context:** A migration plan is an ordered list of DDL steps, and how much of it applies as one unit decides whether a failure midway leaves a half-migrated database behind. PostgreSQL refuses some statements inside a transaction — `CREATE INDEX CONCURRENTLY` among them — so "wrap the whole plan" cannot be permanent policy. Transaction safety is a property of a statement's kind, which the engine already knows; placing boundaries is therefore a decision the planner can make correctly and the user cannot. Tools in this space commonly expose transaction flags or per-step commit points, pushing the choice onto whoever applies the SQL, and a misplaced commit is unrecoverable. A durable decision is needed because the partition is part of the plan's public shape and the generated SQL's behavior.

**Decision:** Transaction boundaries are derived from step semantics, never user-configurable. The planner classifies every step kind as transactional or not and coalesces consecutive transactional steps into one group; a non-transactional step stands alone outside any wrapper. One transaction is the default because every current statement kind is transaction-safe. There is no flag, option, or plan shape that lets a user split, merge, or place a commit boundary; adding a non-transactional step kind is the only way a second group can arise, and its classification is compile-time enforced in the change that introduces it.

**Consequences:** A default migration applies atomically: a statement failing midway rolls the whole plan back, and the gated live suite proves it permanently, with the stripped-wrappers falsification keeping the proof load-bearing. A future statement PostgreSQL refuses inside a transaction gets its own bare group instead of weakening the default, and the renderer carries no per-statement policy beyond following the groups. The classification becomes an obligation on every new step kind — the build fails until it is classified — and the plan's shape grows (`groups` beside `steps`). Users cannot trade atomicity for granularity, so a real need for controlled commit points would require a new ADR superseding this one. [ADR 0001](./0001-generate-never-apply.md) stands: this decides what the generated SQL looks like, not who applies it.
