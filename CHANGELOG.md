## [Unreleased]

### Added

- **Live catalog introspection: tables, columns, and primary keys** — `@schemamill/postgres` bound the `CatalogReader` seam with `catalogReader`, reading a live server's user schemas through one `psql -c` batch — one implicit transaction, one JSON document — with an empty `search_path` and `default_transaction_read_only=on`, and no client-library dependency. The read maps tables in canonical order, columns in attribute order, and primary keys in key order, stripping PostgreSQL's conventional `<table>_pkey` name exactly as the dump importer does; partitioned relations are skipped and named, and unlogged or temporary persistence and the deferred column states — defaults, generation, identity, explicit collation, storage, compression — are flagged and named, with generated suppressing the default flag. Transport failures and payload-contract violations (missing or wrong-typed fields, orphan or duplicate rows) throw; `docs/adr/0011-introspection-transport.md` records the decision. The gated live suite gained `introspection-tracer` (a model with quoted and mixed-case identifiers, composite and conventional primary keys, and a dropped column whose `attisdropped` row must be filtered, asserting an empty `diff` and a deep-equal model against the dump import) and `introspection-flags` (pinning the exact deferred-state diagnostics) ([#55](https://github.com/osama784/schemamill/issues/55)).
- **Workspace container: layout, resolution, and `init`** — `@schemamill/core` gained `resolveWorkspace` and `initWorkspace` plus the `WORKSPACE_DIR_NAME`/`WORKSPACE_MODEL_FILE_NAME` constants: a workspace root is a directory holding a hidden `.schemamill/` directory whose `model.json` is the bare canonical model, and resolution is lexical — no `realpath` — walking to the filesystem root by `dirname`, returning the nearest marker, reporting a corrupt nearest root instead of skipping it, and distinguishing an absent marker from an unreadable one (`workspace-inaccessible`) through a ten-code `WorkspaceDiagnostic` union. `init` creates the target when absent, claims the marker atomically, writes the exact empty model, and refuses a target file, an existing marker (with the `remove <target>/.schemamill to re-create it` repair hint), and a directory inside an existing workspace (ancestors only, so a workspace containing another is allowed). The reader fails closed on unknown keys at every level, validates canonical integer strings, referential actions, sequence data types, and identity generations, and names the failing path. `@schemamill/cli` gained `schemamill init [path]`, printing `Initialized workspace at <absolute path>` and exiting 0, or the diagnostic on stderr and exit 1. The first consuming command, a public writer, snapshots, and studio consumption are deferred ([#54](https://github.com/osama784/schemamill/issues/54)).
- **Core mutation-testing harness** — `@schemamill/core` gained a StrykerJS 10.0.0 mutation-testing setup with `@stryker-mutator/tap-runner` and `@stryker-mutator/typescript-checker` pinned as devDependencies: `pnpm mutation:core` runs the full package mutation run against the existing `node:test` suite, and `pnpm mutation:check` is a scoped sanity check that derives the `src/diff.ts:sameOwner` anchor from the source at runtime, runs a real Stryker run, and fails when the committed config, coverage, or kill signal regresses. A new `Mutation` workflow runs the check and the full run on core-touching PRs, on `workflow_dispatch`, and on a weekly schedule (Node 24 on `ubuntu-24.04`, 60-minute timeout, `packages/core/reports/` uploaded as the `mutation-report` artifact, `if-no-files-found: error`); it is intentionally not part of the required `verify` matrix or the five gates, and no score gate is wired yet (`thresholds.break: null`) — `docs/mutation-testing.md` records the tool evaluation, both commands, the shared config, the CI shape, the survivor-triage protocol, and the anchor's re-aim contract ([#52](https://github.com/osama784/schemamill/issues/52)).
- **Compare prints hazards** — `@schemamill/cli`'s `compare` now plans the pair and prints the same `Hazards:` section `plan` prints, after the diff and separated by one blank line, only when the analysis finds anything, so a clean diff's stdout is unchanged. The hazard step numbers are plan-relative — `compare` prints no step list, so each `step <n>` names the step `schemamill plan` would number `<n>` for the same pair — the help text mentions hazards, and the `hazards` and `identity` compare goldens are re-pinned beside a golden-vs-golden test asserting both commands pin the same block. Exit codes are unchanged ([#51](https://github.com/osama784/schemamill/issues/51)).

### Changed

- **Lint enforces framework-free boundaries and switch exhaustiveness** — `eslint.config.js` now bans `@nestjs/*`, `reflect-metadata`, decorators, and dynamic imports or import-types in `@schemamill/core`, `@schemamill/postgres`, and `@schemamill/cli` (ADR 0005) in each package's existing boundary block, adds `.factory/` to the repo-wide ignores, and enables `@typescript-eslint/switch-exhaustiveness-check` in the shared typed-rules block. The five switches it flagged — `render.ts` `indexStatement`, `hazards.ts` `findIdentityStep`, and `import.ts` `translateColumn`, `translateTableConstraint`, and `referentialAction` — were reconciled by enumerating every remaining union member into the branch its `default` already took, so no program behavior changed ([#53](https://github.com/osama784/schemamill/issues/53)).
- **Index-name canonicalization on import** — `@schemamill/postgres` now canonicalizes a dump's PostgreSQL-generated index name back to unnamed when it is exactly the conventional `<table>_<cols>_idx` for the index's structure, so an index the model declares unnamed (a hand-written `CREATE INDEX ON t (c)`) round-trips through build → dump → import → diff with no spurious drop + add. The pass runs in `finalizeTable` after every statement is translated and before the canonical sort, so the result is independent of statement order, and it keeps the conventional name when an unnamed index of the same structure already exists rather than manufacturing a duplicate unnamed entry. The prediction formula is shared with render's synthesized unnamed drops and moved to `packages/postgres/src/names.ts`. Names outside the formula — truncated at 63 bytes or collision-suffixed (`_idx1`, …) — stay named and still read as remove + add. Compare and plan output now reads unnamed where a dump carried a derivable name, updating the `constraints-indexes` CLI goldens and the live `index-create`/`index-concurrently` import checks, with a new gated `unnamed-index-round-trip` scene pinning the generated catalog names and the unnamed import ([#38](https://github.com/osama784/schemamill/issues/38)).
- **Constraint-name canonicalization on import** — `@schemamill/postgres` canonicalizes PostgreSQL's generated names for a primary key (`<table>_pkey`), unique constraint (`<table>_<cols>_key`), foreign key (`<table>_<cols>_fkey`), and check constraint (`<table>_<column>_check`, or `<table>_check`) back to unnamed when the name is exactly the formula for the constraint's structure, so a dump of a model-declared unnamed constraint round-trips with no spurious name change. The pass runs in `finalizeTable` beside the index pass — after every statement is translated and before the canonical sort — with exact-formula equality and the same pre-scanned twin guard, so any statement order is stable and no duplicate unnamed entry is manufactured; a primary key needs no twin guard, since PostgreSQL allows one per table. A name outside its formula stays named, and a check expression the lexical formula misreads keeps its server name — the fail-safe direction. Compare and plan output now reads unnamed where a dump carried a derivable constraint name, updating the `constraints-indexes`, `all-changes`, and `schema-edges` CLI goldens and the live `constraint-create` scene, whose import check now pins the unnamed primary key, unique, foreign key, and check constraints plus the `EXTRACT(epoch FROM …)` formula miss ([#48](https://github.com/osama784/schemamill/issues/48)).
- **Render refuses duplicate conventional index names** — `@schemamill/postgres`'s `renderSql` now validates the plan before rendering and throws the new exported `RenderRefusalError` when two index statements of one table and polarity resolve to one name — the explicit name for a named index, PostgreSQL's conventional `<table>_<cols>_idx` for an unnamed one — because two creates would collide at apply and two drops would drop one name twice; explicit-vs-explicit duplicates are refused too, while a drop and a create of one name stay legitimate, as an `index-changed` decomposes that way. `@schemamill/cli`'s `plan` catches exactly that class, keeps the plan display on stdout, reports `schemamill: refusing to render: …` on stderr, and exits 1, while every other render failure still crashes; the model is never silently renamed, suppressed, or reordered. The guard is index-only and plan-local, leaving constraint twins, cross-table same-schema name collisions, and truncation boundaries to the named deferred items ([#48](https://github.com/osama784/schemamill/issues/48)).

### Fixed

- **Factory workbench excluded from `format:check`** — `pnpm format:check` no longer flagged the local-only factory workbench; `.factory/` was listed in `.prettierignore` ([#42](https://github.com/osama784/schemamill/issues/42)).

## [0.6.0] - 2026-10-03

### Added

- **Unique and check constraint modeling, import, diff, plan, and render** — `@schemamill/core`'s `Table` gained required `uniqueConstraints` and `checkConstraints` arrays: a `UniqueConstraint` (`name?`, ordered `columns`) is identified by its ordered column list, a `CheckConstraint` (`name?`, opaque whitespace-normalized `expression`) by its expression, and the name travels with a constraint without being identity — structurally identical constraints including the name cancel in the diff, leftovers pair as changed, so a name-only change is a changed constraint while a column-list or expression change reads remove + add. `@schemamill/postgres` imported the inline and `ALTER TABLE … ADD CONSTRAINT` forms, canonicalized to table level because PostgreSQL does not record declaration origin, with `NULLS NOT DISTINCT`, `INCLUDE`, `NO INHERIT`, deferrability, and `NOT VALID` flagged and dropped following the foreign-key precedent (`NOT ENFORCED` travels the parser's same `skip_validation` channel and is flagged under the `NOT VALID` wording, as on the pre-existing foreign-key path), and `ADD CONSTRAINT … UNIQUE USING INDEX` consuming a plain column-list unique index or skipping the whole constraint and naming it. `diff` reported the new table-change variants after the foreign keys, deterministically under any input order; `plan` gained `add-unique-constraint`, `drop-unique-constraint`, `add-check-constraint`, and `drop-check-constraint` — drops in table phases 2–4 in the order index → check → unique, creates in phases 12–14 in the order unique → check → index, every changed constraint decomposing into its drop and add halves, and an added table still emitting `create-table` with columns and primary key only then attaching each member with its own step. `renderSql` rendered `ALTER TABLE … ADD [CONSTRAINT name] UNIQUE (cols)` and `… ADD [CONSTRAINT name] CHECK (expr)`, with unnamed drops synthesizing PostgreSQL's conventional `<table>_<cols>_key` and `<table>_<column>_check` names best-effort.
- **Standalone index modeling, import, diff, plan, and render** — `Table` gained a required `indexes` array of `Index` (`name?`, `unique`, ordered `columns`, optional `concurrently`), identified by name so a rename reads remove + add; a unique constraint is never modeled as, or accompanied by, a standalone index. `@schemamill/postgres` imported `CREATE [UNIQUE] INDEX` inside a minimal plain-btree column-list envelope, skipping any index with an expression element, partial `WHERE`, `INCLUDE`, non-btree access method, non-default ordering, operator class, collation, NULLS ordering, tablespace, storage parameters, or `NULLS NOT DISTINCT` whole and by name, and preserving `CONCURRENTLY` as apply metadata. `diff` paired indexes by name, a flag-only difference not a change. `plan` gained `create-index`, `drop-index`, `create-index-concurrently`, and `drop-index-concurrently` steps around the constraint groups, a changed index decomposing to drop + create; `renderSql` rendered `CREATE [UNIQUE] INDEX [CONCURRENTLY] [name] ON table USING btree (cols)` and `DROP INDEX [CONCURRENTLY] <schema>.<name>`, synthesizing the conventional `<table>_<cols>_idx` name for an unnamed drop and schema-qualifying every drop so an index outside `search_path` resolves.
- **First non-transactional step kinds and multi-group display** — `TRANSACTIONAL` now classifies all twenty-three step kinds, with `create-index-concurrently` and `drop-index-concurrently` `false`, so `groupSteps` stands a concurrent build alone in a bare group. `renderSql` separates groups with exactly one blank line and no comments, wrapping transactional groups as before; `@schemamill/cli`'s `plan` header renders `N steps in M groups:` with `group k of M:` or `group k of M (standalone):` section lines and continuous step numbering, the single-group headers and `No changes.` unchanged ([#33](https://github.com/osama784/schemamill/issues/33)).
- **Live proof for constraints, indexes, and standalone groups** — the gated PostgreSQL harness grew to 31 scenes and 176 tests, 0 skipped: `constraint-create` round-trips named and unnamed single- and multi-column unique and check constraints with `pg_constraint` spot-checks and proves constraint-backed indexes are never double-modeled, `index-create` round-trips plain and unique standalone indexes while partial and expression indexes are skipped whole and by name so the migrated and target imports agree, `index-concurrently` round-trips a wrapped / standalone / wrapped three-group migration with `indisvalid` checked and `CONCURRENTLY` proving apply-only, and `non-public-index-drop` drops a named and a server-named index on an `app` table, with the scene's setup SQL creating the schema, proving the rendered `<schema>.<name>` drops apply and round-trip clean. A falsification wraps the rendered `CREATE INDEX CONCURRENTLY` statement in `BEGIN;`/`COMMIT;` — real PostgreSQL refuses it with `cannot run inside a transaction block` and leaves no index behind, while the same statement bare builds a valid index — proving the standalone group is load-bearing ([#33](https://github.com/osama784/schemamill/issues/33)).

## [0.5.0] - 2026-10-02

### Added

- **Atomic transaction groups** — `@schemamill/core`'s `Plan` gained `groups: readonly TransactionGroup[]`: `TransactionGroup` is `{ start, end, transactional }` with half-open indices into `steps`, non-empty groups tiling the step list in order and `transactional: false` marking a standalone group that applies outside any wrapper, and a compile-time exhaustive `TRANSACTIONAL: Record<Step['kind'], boolean>` classification — all fifteen step kinds transactional today — feeds `groupSteps`, which coalesces consecutive transaction-safe steps and isolates a non-transactional step, with `plan()` computing the partition once. `@schemamill/postgres`'s `renderSql` walked `plan.groups` and wrapped each transactional group in `BEGIN;`/`COMMIT;`, a standalone group bare, with no blank lines and the empty plan still the empty string. `@schemamill/cli`'s `plan` header read `N steps in one transaction:` (singular `1 step in one transaction:`) for the single-group plans `plan()` produces today, the plain `N steps:` header staying the fallback for the deferred multi-group wording, and the empty plan `No changes.`. The gated live-PostgreSQL suite gained two always-on tests: a rollback proof — a mid-plan statement corrupted to name a missing relation, applied with `psql` `ON_ERROR_STOP=1`, re-dumped, imported, and required to diff empty against the baseline — and its falsification, the same corrupted SQL with the wrapper lines stripped leaving the earlier statement's effect behind; the existing scenes stayed green under the wrapped SQL ([#30](https://github.com/osama784/schemamill/issues/30)).

## [0.4.0] - 2026-10-01

### Added

- **Plan hazards** — `@schemamill/core` gained a `Hazard` discriminated union — `increment-zero`, `cache-nonpositive`, `bounds-inverted`, `start-out-of-bounds`, `bound-out-of-type-range`, and `bound-tightened`, each carrying the plan-step index and its structured values — and widened the dialect seam to `HazardAnalyzer<Model, Plan, Hazard>` with `analyze(baseline, target, plan)`. `@schemamill/postgres` gained `analyzeHazards`, bound as `hazardAnalyzer`: sequences matched by schema and name and identity columns by table and column, each target checked for the five definite violations in PostgreSQL's order — `increment-zero` first, then the `MAXVALUE` and `MINVALUE` type-range pair, each bound checked against both ends of its type's range, `bounds-inverted`, `start-out-of-bounds`, and `cache-nonpositive`, every comparison a `bigint` over the stored decimal strings — with a matched entity's tightened `minValue`/`maxValue` reported as `bound-tightened` on the step that carries the change (`create-sequence`, `alter-sequence`, `add-identity`, `alter-identity`, or the `alter-column` type conversion that moves a bound), suppressed when the entity has any definite hazard and skipped for a recreated identity. `@schemamill/cli`'s `plan` printed a `Hazards:` section between the step list and the SQL, only when non-empty, one `step <n> <kind>: <clause>` line per hazard, with `compare`, the rendered SQL, and exit codes untouched. Analyzer unit tests pinned every kind, the boundaries, suppression, and determinism; a new `hazards` CLI golden scene pinned all six kinds, and `identity.plan.txt` was re-pinned to carry its conditional line.

## [0.3.0] - 2026-09-30

### Added

- **Identity column modeling and import** — `@schemamill/core` gained an optional `identity` on `Column` — the `GENERATED ALWAYS`/`GENERATED BY DEFAULT` mode, an optional schema-qualified `sequenceName`, and effective `increment`, `minValue`, `maxValue`, `start`, `cache`, and `cycle` options, every numeric value an exact 64-bit integer in canonical decimal form, never a JavaScript `number` — with `effectiveIdentity` normalizing omitted options and `NO MINVALUE`/`NO MAXVALUE` to the engine defaults, including the direction-dependent bounds of descending identities, and `canonicalIntType` resolving an as-written integer type to `smallint`, `integer`, or `bigint`. `@schemamill/postgres` imported the identity forms a `pg_dump` carries — inline in `CREATE TABLE` and `ADD COLUMN`, `ALTER TABLE … ADD GENERATED … AS IDENTITY`, `SET GENERATED` and sequence-option `SET` clauses, and `DROP IDENTITY` — with an unqualified `SEQUENCE NAME` resolved to the table's schema and a cross-schema name flagged, and the unsupported forms — `RESTART`, `LOGGED`/`UNLOGGED`, `AS`, `OWNED BY`, and non-integer column types — flagged with named diagnostics.
- **Identity diff, plan, and render** — `diff` reported a column's identity as the `identity` part of its `column-changed` entry: additions and removals carried the one descriptor, a stated sequence-name mismatch was a recreation carrying the target descriptor, and two identities compared as a change with only their differing options in the fixed order `generated`, `increment`, `minValue`, `maxValue`, `start`, `cache`, `cycle` — effective values throughout, and a name absent on either side a don't-care — while a column-type change between canonical integer types applied the engine's `AS` conversion to the baseline identity's bounds, exactly like a sequence data type change. `plan` gained `drop-identity`, `add-identity`, and `alter-identity` steps — drop first, ahead of the table phases and the sequence that replaces it, and add/alter last, after sequence drops — carrying the full effective descriptor for an add and only the differing fields for an alter — a removed column or table carries its identity away in its own drop, so only an identity on a surviving column becomes a `drop-identity` — and turning conversions between sequence-backed columns and identity into their step sequences in both directions (`DROP DEFAULT` → `drop-sequence` → `add-identity`, and `drop-identity` → `create-sequence` → `SET DEFAULT`). `renderSql` rendered `add-identity` as one full-explicit `ALTER TABLE … ADD GENERATED … AS IDENTITY ( … )` with the plan's effective values, `alter-identity` as one statement of `SET` clauses in the diff's fixed field order, and `drop-identity` as `ALTER TABLE … DROP IDENTITY`; `compare` printed identity differences as `identity:` sub-lines under the changed column, and `@schemamill/cli` pinned an `identity` golden scene covering add, drop, recreation, tuning, and conversions in both directions.

### Fixed

- **Converted bounds in `compare`** — when an `AS` conversion or an integer column-type transition moved a bound, `diff` flagged the reported `minValue`/`maxValue` as `converted` and `compare` printed it as `<value> (converted)`, so a bound the engine's conversion produced no longer read as an as-written baseline value.

## [0.2.0] - 2026-09-29

### Added

- **Sequence modeling and normalization** — `@schemamill/core` gained a first-class `Sequence` entity and a `sequences` array on `Model`: schema-qualified identity, `dataType` (`smallint`, `integer`, `bigint`), `increment`, `minValue`, `maxValue`, `start`, `cache`, `cycle`, and an optional `ownedBy` (`{ table, column }`). Every numeric option was stored as an exact 64-bit integer in canonical decimal form, never a JavaScript `number`, so the type bounds (`9223372036854775807` and friends) survived intact; `effectiveSequence` normalized omitted options and `NO MINVALUE`/`NO MAXVALUE` to the engine defaults, including the direction-dependent bounds of descending sequences.
- **Sequence import** — `@schemamill/postgres` imported `CREATE SEQUENCE` (options and inline `OWNED BY`) and the `ALTER SEQUENCE` options that map to modeled fields — `AS` type, increment, min/max, start, cache, cycle, and `OWNED BY`/`OWNED BY NONE` — applying them in the engine's fixed order, converting old-type-default bounds on `AS` changes, and modelling the separate `ALTER SEQUENCE … OWNED BY` statements `pg_dump` emits. `RESTART` (sequence state), renames, `SET SCHEMA`, `setval` calls, and dump-side `DROP SEQUENCE` stayed skip-and-named, as did unsupported options and values; `UNLOGGED` and `TEMPORARY` sequence persistence was flagged and dropped, like a table's.
- **Sequence diff, plan, and render** — `diff` gained a deterministic sequences group with field-level changes (`dataType`, `increment`, `minValue`, `maxValue`, `start`, `cache`, `cycle`, `ownedBy`), comparing effective values so an omitted option and its explicit default were not a change and, on a data type change, comparing bounds against the engine's `AS` conversion so the plan restated any bound the conversion would have moved; `plan` gained `create-sequence`, `alter-sequence`, and `drop-sequence` steps ordered by policy — creates, ownership detaches before a removed owner, the table phases, ownership attaches/re-owns, option alters, then drops — suppressing an explicit `DROP SEQUENCE` when the plan also removed the table or column that owned it, because PostgreSQL drops an owned sequence with its owner; and `renderSql` rendered the canonical full-explicit `CREATE SEQUENCE`, one `ALTER SEQUENCE` statement per changed field set (ownership included), and `DROP SEQUENCE`. `@schemamill/cli` gained a `sequences` golden scene covering sequence add and drop, an owned sequence for a new table, option alters, ownership detach and re-own, and drop suppression.

### Changed

- **`compare` and `plan` outputs include sequences** — sequence changes now render as `sequence <schema>.<name>` blocks after the table changes in `compare`, with one option per line and field-level changes; `plan` numbers sequence steps inline in policy order. The previous sequence skip diagnostics disappeared: `CREATE SEQUENCE` and mapped `ALTER SEQUENCE` statements are part of the model now.

## [0.1.0] - 2026-09-29

### Added

- **PostgreSQL parser foundation** — `@schemamill/postgres` pinned `libpg-query` (PostgreSQL 18 grammar, WASM) and gained a `pg_dump`-style dump preprocessor: psql meta-commands and `COPY … FROM stdin` data blocks were skipped and named, statements were split safely around dollar quotes, comments, and escaped strings, and every statement was parsed on its own so one bad statement never sinks a dump — parse failures were reported with positions.
- **Import dumps into the canonical model** — `@schemamill/postgres` gained `importDump`: a `pg_dump`-style dump was translated into the canonical model — tables, columns with as-written type and `DEFAULT` text, primary keys, foreign keys, schema-qualified identity — and everything outside the first-slice subset was skipped or flagged with a named, positioned diagnostic.
- **Diff two models** — `@schemamill/core` gained `diff(baseline, target)`: two canonical models were compared into a deterministic list of changes — tables added, removed, and changed, with nested column, primary-key, and foreign-key changes — matched by schema-qualified table identity and by column name, with no rename detection (renames read as remove plus add) and the stored `type` and `default` text compared exactly as written. Comparison output was independent of input array order, and payloads were returned as independent copies.
- **Migration planning and SQL rendering** — `@schemamill/core` gained `plan(baseline, target)`, which expanded a diff into dependency-ordered steps: foreign keys were dropped before what they depend on and added after what they reference, changed primary keys and foreign keys split into drop and add halves, removed tables were dropped dependents-first with deterministic cycle-breaking, and surviving foreign keys were set aside around primary-key changes. `@schemamill/postgres` gained `renderSql`, which rendered a plan as deterministic, reviewable migration SQL behind the `SqlRenderer` seam — schema-qualified, with identifiers quoted only when PostgreSQL requires it — and golden tests pinned the output.
- **Command-line compare and plan** — `@schemamill/cli` gained `schemamill compare <baseline> <target>` and `schemamill plan <baseline> <target>`: the first printed the diff as signed table blocks with their columns, primary keys, and foreign keys, with field-level changes anchored on the foreign key's pairing identity; the second printed the numbered dependency-ordered steps followed by the rendered migration SQL. Both read DDL dumps, wrote only the artifact to stdout and per-side import diagnostics to stderr (with `--verbose` naming every skip and flag, positions included), and exited 1 on a read failure, a thrown import, or any parse failure — the artifact still printed in the last case.
- **Verification harness and dogfooding** — `@schemamill/postgres` gained a live-PostgreSQL harness (`src/live-pg.test.ts`, scenes in `src/live-scenes.ts`) gated on `SCHEMAMILL_TEST_PG_URL`: unset, the suite was skipped with a reason; set but unreachable, it failed loudly. For each scene — the five golden scenes plus the regression shapes that caught the first slice's real ordering bugs, and unnamed-constraint drops under PostgreSQL's conventional names — it created fresh databases, built the baseline and target databases with `renderSql(plan({ tables: [] }, model))`, applied `renderSql(plan(baseline, target))` to the baseline, dumped both with `pg_dump --schema-only --no-owner --no-privileges`, imported both dumps, asserted no error diagnostics and an exactly empty `diff`, and spot-checked catalog facts: tables, columns by ordinal position, types, `NOT NULL`, defaults, primary-key names, foreign-key `confdeltype` actions, and foreign-key enforcement probes. `@schemamill/cli` gained golden tests (`src/goldens.test.ts`) that pinned the exact stdout of `compare` and `plan` for a fixture dump pair exercising every change kind, with fixtures under `packages/cli/test/fixtures` and goldens under `packages/cli/test/goldens`. A `verify-postgres` CI job ran the harness on Node 24 against a `postgres:18` service, with PGDG `postgresql-client-18` tools on `PATH`.

### Documentation

- **Branch/PR and changelog workflows** — adopted a feature-branch → `dev` → `main` flow with `gh` PRs and a Keep a Changelog–based `CHANGELOG.md`, captured as repo skills.
- **First-slice plan** — [`docs/plans/first-slice.md`](docs/plans/first-slice.md) scopes the first end-to-end path: read two PostgreSQL DDL dumps, compare, and render the migration plan as migration SQL.
